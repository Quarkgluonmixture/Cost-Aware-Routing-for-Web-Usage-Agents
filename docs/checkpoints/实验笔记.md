## 4. 手动逐模式分析（2026-04-06） [finding]

对 DOM 和 SoM 模式分别进行了人工分析，结论见 `docs/analysis/classifieds/`：

### DOM 模式（`B1_DOM_digest.md` §四）

**脚手架/DOM 结构性缺陷（109 例，51.2%）**：
1. **视觉信息结构性不可达** — DOM 不含图片语义，颜色/款式匹配类任务结构性无法完成（99 例，占 scaffold 缺陷的 91%）
2. **非视觉脚手架问题**（10 例）— 筛选器 UI 定位困难、AXTree 信息不足、JS 弹窗不可达等

**模型能力问题（104 例，48.8%）**：搜索循环（29）、导航循环（18）、事实推理错误（15）、过早结束（12）等

**信息瓶颈**：95% 的详情页 AXTree 不包含商品描述文本。DOM 模式理论成功率上限约 55%（非视觉任务占比）。但实际 adjusted SR 仅 0.85%（21 个 raw 成功中 19 个是 visual FP，见 §20）。

### SoM 模式（`B1_SOM_digest.md` §二）

**SoM 表征结构性缺陷（4 类）**：
1. **标注遮挡** — 青色 mark 框覆盖缩略图左上角（~200×170px），遮挡关键视觉区域
2. **空间布局丢失** — marks 为线性序号列表，多列 grid 退化为一维序列
3. **深度滚动 ID 幻觉** — viewport 外元素无 mark，模型引用不存在的 ID
4. **text-over-vision bias（30 例，占 86%）** — 4B VLM 系统性忽略截图视觉细节，依赖 `[SOM_MARKS]` 文字标签决策。SoM 对小模型反而提供了"不看图的捷径"

> **关键发现**：SoM 表征对模型视觉能力有最低门槛要求。4B 模型上 SoM ≈ DOM（文字主导），与 GPT-4V 上 SoM 有效性的文献结论形成对比。**后续修正**：§23 证明 SoM 最终 SR（20.5%）远超 DOM（8.97% raw / 0.85% adj），Mirage Effect（图片触发质变推理路径）是主因，而非文本差异。

## 5. busy:1 中间态问题发现与修复（2026-04-04） [bug]

实验运行中发现 VWA 底层的 `wait_for_load_state("networkidle", timeout=2000)` 超时过短，远程 Classifieds 站点经常来不及加载完，导致 DOM 包含 `busy: 1` 标记。

**原始实现的问题**：busy:1 检查在 LLM 调用之后，仅覆盖 action 为 wait，但 LLM 推理（tokens + latency）已经浪费：

```
1. 拿到 obs（busy:1 的半加载页面）
2. 准备 SoM（只有 1 个 mark）
3. 调用 LLM 推理 ← 浪费
4. 检查 busy:1 → 覆盖 action 为 wait
```

**旧 Run 影响量化**：

|                           | DOM        | SoM        |
|---------------------------|------------|------------|
| busy:1 步数占比           | 11.8%      | 24.5%      |
| 受影响 task 比例          | 55.6%      | 80.1%      |
| 到 max_steps 失败的 task 平均浪费步数 | 4.7 步（15.7%） | 9.8 步（32.8%） |

SoM 的 busy:1 率是 DOM 的 2 倍——SoM 处理链更长（截图 → CDP bbox → 标注渲染），更容易在 2s 内来不及加载完。这是一个**公平性问题**：SoM 的有效步数预算被 busy:1 大量侵蚀，DOM vs SoM 的成功率对比被污染。

**修复方案**（已实现并验证）：将 busy:1 检查提到 LLM 调用之前，且 busy:1 步不计入 max_steps 预算（免费等待）。重跑后 DOM 和 SoM 的 busy:1 占比均降至 **0%**。

## 7. Logprobs 置信度信号提取（2026-04-07） [infra]

实验中途加入了 logprobs 提取模块，作为 Phase 2 confidence-based routing 的前置依赖。

### 为什么必须做

文献中两篇直接相关工作验证了 logprobs 在 cost-aware agent 中的基础设施地位：

| 论文 | logprobs 用法 | 效果 |
|------|--------------|------|
| **AVR**（Adaptive Vision-Language Routing, arXiv:2603.12823） | VLM grounding 坐标的 logprob 作为置信度，低于阈值 → 升级到更强模型/表征 | ScreenSpot-Pro 上成本降低 78%，准确率仅降 0.8pp |
| **CATTS**（Agentic Test-Time Scaling, arXiv:2602.12276） | margin-gated confidence（top-1 − top-2 logprob），低 margin → 多采样 + 语义去重投票 | WebArena-Lite 上 token 消耗降低 56%，成功率反升 4.7% |

### 对 P79 的三个不可替代角色

1. **路由决策的量化依据**：当前 router 仅依赖 DOM 节点数量和连续无变化步数（外部观测），logprobs 直接回答"模型对当前 action 有多确信"
2. **小模型置信度校准的研究空白（文献 Gap 6）**：4B 模型的 logprob 是否与成功率单调相关？是否 overconfident？Phase 1 数据可填补此空白，构成论文 Section 4.2 的实证贡献
3. **Phase 2 阈值设定的数据基础**：500+ 步的 (logprob, success) 样本可用 ROC 曲线精确设定路由阈值，避免凭经验盲设

### 实现情况

已在 `qwen3vl_agent.py` 中实现 `_compute_confidence()` 方法（`output_scores=True, return_dict_in_generate=True`），提取四个指标：
- `mean_logprob` / `min_logprob`：平均/最低 log probability
- `mean_margin` / `min_margin`：平均/最小 top-1 与 top-2 gap

分析脚本 `analyze_confidence_calibration.py` 已就绪，待 Reddit 站点跑完后进行校准分析，输出包括 reliability diagram、ECE/MCE、AUROC 等。

## 9. 表征选择与模型能力的交互效应（2026-04-07） [finding]

Read More, Think More（论文 [2]）发现：高能力模型用 HTML 反而更好（+17.5pp），低能力模型用 a11y 更好。这和我们在 SoM 上观察到的 text-over-vision bias 是同一个底层现象——**最优表征不是绝对的，是模型能力的函数**。

这意味着 Phase 2 router 的理论框架可以更丰富：不只是"根据任务难度选表征"，而是"根据任务难度 × 模型能力选表征"。在单模型（4B）实验里这个交互效应看不到，但如果后续引入 B0（API 模型），可以直接测试：4B 用 DOM 最好的任务，API 模型是不是用 SoM 反而更好？如果是，router 就不只是 cost-aware，而是 **capability-aware**。

## 10. 数据质量保障（2026-04-07） [infra]

### 任务重启去重

Watchdog 重启会在 JSONL 中产生重复行（step_idx 从 0 重置）。已创建统一的 `io_utils.read_jsonl_dedup()` 函数，替换了 5 处独立实现，所有分析脚本均自动去重。

### VWA 结构性不可达任务

在 VWA 中发现了一批结构性不可达任务（`<select>` 三层过滤 bug、viewport 限制等），Agentic Web 评测框架中是直接绕过的。我们的处理方式：

- **判定标准**：同一 task 在所有 condition（dom + som + vision）下均失败 → 强候选 structurally unsolvable
- **区分假阳性**：若有 B0 强模型 baseline，可交叉验证；否则同时报告 raw 和 adjusted 成功率
- **实施方式**：纯数据驱动，等三站全部跑完后在分析脚本中一行 `groupby` 即可算出，不需修改 runner 或 hardcode 列表

```
raw success rate:      X%  (N tasks)
adjusted success rate: Y%  (N - K tasks, excluding K tasks failed across all conditions)
```

### N/A Reference Task 假阳性

VWA 的 `ua_match` 评测器使用 LLM 判断 agent 答案是否与 reference 语义匹配。当 reference 答案为 "N/A"（不可回答类任务）时，agent 未调用 `finish` 而由 runner 自动追加的空 answer（`create_stop_action("")`）也能通过匹配，产生虚假成功。

**影响范围**：Classifieds 站 234 个 task 中有 10 个 N/A reference task（24, 135, 164, 167, 189, 191, 194, 195, 196, 220），详见 §27 修正。

**修复方案**：
- `analysis.py` 中新增 `_load_na_task_ids(site)`，扫描 VWA task config 中 `eval.reference_answers.fuzzy_match == "N/A"` 的 task
- `ep_df` 中标记 `is_na_reference` 列，输出 `na_reference_tasks.csv`
- `analysis_summary.json` 中同时报告 `raw_success_rate` 和 `adjusted_success_rate`（排除 N/A 假阳性）

### Type 操作全选变蓝

VWA 底层 Playwright 的 `type` 方法在执行搜索框输入时，偶尔导致页面文本被全选高亮（蓝色覆盖）。选区从输入框扩散到整个页面，后续截图中所有文本呈蓝色高亮状态（如 task_17 step 9）。

**影响**：DOM 模式无影响（读 AXTree 不看截图）；SoM/Vision 模式会严重干扰视觉理解。属于 VWA/Playwright 环境层面已知行为，详见 `docs/analysis/classifieds/B1_findings.md` §6.4。

## 15. Predictive Entropy 信号补充（2026-04-09） [literature]

### 文献调研结论

基于 8 篇相关文献的系统调研（见 `docs/literature/logprob_signals.md`），核心发现：

1. **原始 logprob 不可靠**：小 VLM 的 raw token logprob 校准差，分布偏移时过度自信，多步轨迹中误差累积
2. **校准是关键**：temperature scaling 或 learned mapping 在 held-out set 上校准后，logprob 才适合做路由信号
3. **Entropy 与 margin 互补**：margin 只看 top-2 差距（分布是否尖锐），entropy 看整个分布散度（捕捉"top tokens 都不确定"的情况）
4. **Semantic entropy / attention entropy**：前沿但证据不足，不值得在 4B 模型上投入

### 新增指标

在 `_compute_confidence()` 中增加两个 predictive entropy 指标：
- `mean_entropy`：各 token 预测熵的均值（H = −∑ p log p），衡量整体不确定性
- `max_entropy`：最大单 token 熵，标识最不确定的决策点

计算开销几乎为零（复用已有的 `log_softmax` 结果，一行 `-(probs * log_probs).sum()`）。

### 数据覆盖

| 数据段 | 有 entropy | 估计量 |
|--------|-----------|--------|
| DOM classifieds 0-186 | ❌ | 186 tasks |
| DOM classifieds 187-233 | ✅ | 48 tasks |
| SoM / Vision classifieds | ✅ | 468 tasks |
| 其他 3 站 × 3 模式 | ✅ | ~2100 tasks |

>95% 的未来数据将包含 entropy 指标。分析脚本对缺失 entropy 的旧 episode 自动跳过（optional field）。

### 完整置信度信号集（6 指标）

| 信号 | 维度 | 用途 |
|------|------|------|
| mean_logprob / min_logprob | 绝对信心 | 模型对 action 的整体/最弱信心 |
| mean_margin / min_margin | 区分度 | top-1 vs top-2 的选择确定性 |
| mean_entropy / max_entropy | 分布散度 | 全分布不确定性（捕捉 margin 遗漏的多候选散射） |

Phase 2 路由计划：B1 全部跑完 → `analyze_confidence_calibration.py` 评估 AUROC → held-out set 上 temperature scaling → percentile-based 阈值设定。

## 18. Mirage Effect 与 Text-Over-Vision Bias（2026-04-09） [literature]

### 文献关联

Mirage 论文（Asadi et al., arXiv:2603.21687, Stanford, 2026-04）发现 VLM 在**完全没有收到图片**时，依然能自信地描述视觉特征并在多模态 benchmark 上取得 70-80% 的原始准确率。论文称之为 "mirage effect"——模型构建虚假的感知叙事，表现得好像图片存在。

这一发现与 B1 实验中的三个独立观察形成 1:1 对应：

| Mirage 论文发现 | B1 实验观察 |
|---|---|
| VLM 无图仍自信描述视觉特征 | DOM 模式 8.97% 成功率中 90.5% 是 visual lucky hits——模型无视觉输入，纯靠文本线索导航到正确页面 |
| 无图准确率达有图的 70-80% | SoM text-over-vision bias：4B 模型系统性忽略截图，依赖 `[SOM_MARKS]` 文字标签决策 |
| Mirage-mode > Guess-mode（假装有图 > 明确告知无图） | SoM 曾因 bug 未传入图片（仅 SoM marks 文本），成功率反而提升 |

### Mirage-mode vs Guess-mode 机制

论文 Section 4.1 揭示了两种不同的推理机制：

- **Guess-mode**（对应 DOM 模式）：模型意识到没有图像 → 保守的纯文本推理，依赖先验和答案分布
- **Mirage-mode**（对应 SoM-without-image bug）：消息结构暗示图像存在 → 模型进入不同推理路径，利用训练中学到的隐藏文本-视觉关联模式

论文原文：*"In mirage-mode, the model appears able to exploit additional hidden structure... it behaves as though an image exists, constructs a plausible perceptual narrative, and in doing so accesses cues or associations that are not captured by standard 'no-image guessing' controls."*

SoM-without-image 的消息格式（`[SOM_MARKS]` 列表 + 暗示截图存在的结构）恰好触发了 mirage-mode，激活了比 DOM 模式更强的推理路径。

### Phantom-SoM：一种低成本的路由中间层

这个发现暗示了一种非正统的路由策略——在 DOM 和完整 SoM 之间插入一个"幻影 SoM"层：

| 模式 | 内容 | 成本 | 推理模式 |
|---|---|---|---|
| DOM（cheap） | AXTree 纯文本 | 低 | Guess-mode |
| **Phantom-SoM**（cheap） | SoM marks 文本 + **无图** | ≈ DOM | Mirage-mode |
| Full SoM（expensive） | SoM marks + 截图 | 高 | 真实多模态 |

路由链：`DOM → [confidence low?] → Phantom-SoM → [still low?] → Full SoM`。第一次升级几乎零成本（只改文本格式），第二次升级才付出图片成本。

### 局限性

1. **利用训练 artifact**：mirage effect 是 VLM 联合训练的副作用，不是真实能力。模型特异性强——4B 上可能有效（text-over-vision 本来就强），235B 上可能反而有害（大模型可能真的在用视觉信息）
2. **不可解释性**：难以向 reviewer 解释"故意不传图片让模型产生视觉幻觉来提升成功率"
3. **Benchmark 污染**：如果 VWA 的 `url_match` 评测让无图模式也能得高分，说明 benchmark 本身有 mirage 漏洞

### 对论文的价值

即使不作为正式路由策略，这个发现有三个方向的贡献：

1. **独立复现 Mirage 效应**（Section 4 Analysis）：在交互式 web agent 场景（非静态 QA）中观察到 mirage effect，比论文的 benchmark QA 场景更强
2. **为 text-over-vision bias 提供理论根基**：之前只有经验观察（"4B 模型不看图"），Mirage 论文提供了机制解释——这是 VLM 联合训练的系统性 artifact
3. **B0 vs B1 的 mirage 强度对比**：如果 235B 的 mirage effect 更弱（真的在用视觉信息），那 `(SoM - DOM)_B0 > (SoM - DOM)_B1`，直接支撑"最优表征是模型能力的函数"假设
4. **Phantom-SoM ablation**：小规模（~50 tasks）ablation 即可量化 4B 模型对视觉信息的真实依赖度，insight 密度高、成本低

### 后续计划

- 等 B1 三模式 + B0 初步数据就绪后，补做 Phantom-SoM ablation（~50 tasks classifieds）
- 对比 B0 vs B1 的 `SoM成功率 - DOM成功率` 差值，量化模型规模对 mirage effect 的调节作用

## 19. Tool Calling 线性电路与 Action Selection（2026-04-09） [literature]

### 文献关联

"Tool Calling is a Linear, Steerable Circuit in Language Models"（Anonymous ACL submission, 2026）发现 LLM 的 tool 选择决策住在残差流的一个低维线性子空间中。论文**明确测试了 Qwen 3 4B**（B1 使用的同一模型家族），主要发现：

1. **15 个 tool 只需 ~10 个方向**即可分离（PCA top-10 捕获 90.2% 方差）
2. **三阶段流水线**：早期层（0-10%）→ tool-specific 特征激活；中间层（50-80%）→ attention head 从 context 读取 tool name 和实体 token；晚期层（85-100%）→ 线性子空间中做最终选择
3. **Steering 有效**：加一个 mean-difference 方向向量可以 80-93% 准确率切换 tool 选择，模型自动重写整个 JSON argument 以匹配新 tool
4. **模型"知道"但"说不出"**：base model 内部已编码正确 tool（77-89%），但生成输出只有 3-61%。Instruction tuning 教会模型表达已有知识
5. **Error prediction**：top-2 tool 的 cosine gap 小 → 错误率高。标记低于中位数的 gap 可捕获 92% 的错误

### Action Type = Tool Selection

P79 agent 的输出 `{"action_type": "click", "element_id": 175}` 在结构上就是 tool calling：

- `action_type` ∈ {click, type, scroll, wait, back, forward, finish, tab_focus} = **8 个 tool**
- `element_id` / `text` / `delta` = **tool arguments**

论文对 Qwen 3 4B 的发现（steering 在 L23+ 有效，PCA 90.2%）直接适用于 B1 的 action selection。8 个 action type 比论文的 15 tool 更少，线性子空间可能只需 ~7 维。

### 对 Phase 2 路由的启示：表征层置信度信号

| 信号层级 | 信号 | 来源 | 优势 | 限制 |
|---|---|---|---|---|
| 输出层（当前） | logprob / margin / entropy | token 概率 | B1 + B0 均可用 | Mirage 论文表明可能过度自信 |
| **表征层**（论文） | action type 间 cosine gap | 倒数第二层 activation | 直接测量决策确定性，不受输出层校准影响 | 需白盒访问，仅 B1 可用 |

论文的 cosine gap 信号比 logprob 更强：它在模型内部决策层面直接测量"click 和 scroll 谁赢"的确信度，绕过了输出层的校准问题。对 Phase 2 router，如果 logprob 校准不够好（4B 模型大概率如此），activation-level cosine gap 可作为补充路由信号。

### 解释 B1 观察到的失败模式

"模型知道但说不出来"直接解释了两个系统性失败：

- **极少 scroll up**（B1_DOM_digest §5）：DOM 模式 scroll up 仅 3.7%（24/646），SoM 为 11.2%（48/430）。模型不是完全不会，但在需要主动回翻的场景下严重不足。视觉信息帮助感知空间位置（SoM 3x），说明内部表征可能存在但输出层激活不充分
- **未点进详情页就 finish**（§2.3）：模型内部犹豫在 click 和 finish 之间，但 finish 方向在输出层更容易被选中

### Cosine Select + Generate ↔ M4 两阶段模块

论文的流水线：(1) 从 activation 读取 tool 身份 → (2) 填入 tool name → (3) 模型只生成 arguments。

这和 Phase 3 M4（planner + grounder）结构等价：
- Planner = cosine select（决定 action_type）
- Grounder = generate（生成 element_id、text 等参数）

论文证明 action selection（线性）和 argument generation（非线性）的分离在 Qwen 3 4B 上 match 或 beat 端到端生成，为 M4 设计提供了 mechanistic 理论支撑。

### 与 Mirage 论文的交叉

| 论文 | 发现 | 对应 P79 启示 |
|---|---|---|
| Mirage | 消息格式影响推理模式 | Phantom-SoM：改格式触发多模态推理路径 |
| Tool Calling | Action selection 线性可操控 | 在 residual stream 加方向向量修正 action type |

组合后的极端方案：不换观测模式、不重新推理——在 Qwen 3 4B 的 L23 层加方向向量，增强 scroll up 方向的激活（当前 DOM 3.7% / SoM 11.2%，仍有很大提升空间）。零额外 token 成本。需要白盒访问 + 预计算方向向量，超出当前范围但作为 future work 有吸引力。

### 对论文的实际价值

**可直接引用**：
1. M4 两阶段设计的理论基础——action selection 和 argument generation 的分离有 mechanistic 证据
2. Output-level confidence 之外存在 representation-level 信号（discussion 中补充）
3. Qwen 3 4B 的具体数据直接可引用（steering L23+, PCA 90.2%）

**Future work——离线 Activation 提取与信号评估**：

核心思路：B1 baseline 已有全部 episode 数据（observation + prompt + success label），**不需要重跑实验、不需要环境交互**。离线对已有输入做 forward pass（不 generate），截取中间层 hidden states 即可。

**Step 1：离线 Forward Pass 提取 Activation**
- 从已有 episode JSONL 读取每步的 observation（DOM text / SoM image）+ 完整 prompt
- 喂给 Qwen 3 4B 做一次 forward pass（`output_hidden_states=True`，不调 `generate`）
- 保存倒数 3-5 层的 last-token hidden state（~4096 dim × 5 层 × float16 ≈ 40KB/step）
- 预计规模：234 tasks × ~10 steps ≈ 2300 次 forward，4B 模型在 GB10 上几分钟

**Step 2：Action Type 子空间 PCA**
- 按 action_type 标签分组（click/type/scroll/finish/...），计算各组 mean activation
- PCA 降维，测量 8 个 action type 需要多少维度分离（论文 15 tool → 10 维，预期 8 action → ~7 维）
- 可视化 action type 在子空间中的分布

**Step 3：Cosine Gap 路由信号评估**
- 计算每步 top-2 action type 方向的 cosine gap
- 和已有 output-level 信号（logprob margin / entropy / verbalized confidence）做 AUROC 对比
- 预期：cosine gap 在 4B 模型上显著优于 logprob margin（因为输出层校准差，但内部表征可分性强）
- 若验证成功，cosine gap 可作为 Phase 2 router 的补充/替代信号

**Step 4（可选）：Activation Steering 修正系统性偏差**
- 预计算方向向量：`scroll_up - scroll_down`、`click - finish` 的 mean-difference
- 在 forward pass L23+ 层注入方向向量，测试能否翻转 action 选择
- 零额外 token 成本，零额外推理调用——只需在 forward 中间插一个向量加法
- 目标：修正 "69/69 scroll 全部向下"、"premature finish" 等系统性偏差

**关键约束**：仅对 B1（本地白盒模型）可行，B0（API）无法访问 intermediate activations。这反而强化了 cost-aware routing 的价值——本地小模型可以做 API 做不到的 representation-level 优化。

## 20. Visual False Positive 检测接入 Cross-Representation Analysis（2026-04-09） [finding]

### 问题

DOM 模式 21 个成功 episode 中有 **19 个是假阳性**——visual task（需要看图/辨颜色/匹配图片的任务）在无图的 DOM 模式下碰巧通过文本匹配得分（`url_match` 类评测器只检查 URL 是否到达目标页，agent 碰巧导航到了正确页面）。

这导致所有 cross-representation 分析指标严重失真：

| 指标 | Raw（失真） | Adjusted（修正后） |
|------|------------|-------------------|
| DOM SR | 9.0%（21/234） | **0.85%（2/234）** |
| Oracle ceiling（union SR） | 12.4% | **4.7%** |
| DOM 独占成功集（only_dom） | 19 tasks | **1 task** |
| Best single mode | dom | **som** |
| R3 oracle DOM 选择数 | 20 | **2** |

修正前 DOM 看起来是最强模式、oracle ceiling 看起来有 12.4%，实际上绝大部分 DOM "成功" 都是假阳性。

### 检测逻辑

复用 `p79/experiment/analysis.py` 已有的 `_load_visual_task_ids(site)` 函数，该函数通过两个信号检测 visual task：
1. Task config 中有 `image` 字段（显式图片输入任务）
2. Task intent 包含视觉关键词（`_VISUAL_TASK_KWDS`：颜色词、"in the image"、"same item" 等）

假阳性标记规则：**仅 DOM 模式**——visual task + success = false positive。SoM（有截图）和 Vision（有截图）的 visual task 成功是真阳性。

### 三站 Visual Task 比例

| 站点 | has_image（显式图片任务） | kwd_only（颜色/外观关键词） | 非视觉 | visual 合计 |
|------|--------------------------|----------------------------|--------|------------|
| classifieds | 68 (29%) | 94 (40%) | 72 (31%) | 162 (69%) |
| reddit | 150 (71%) | 27 (13%) | 33 (16%) | 177 (84%) |
| shopping | 169 (36%) | 100 (21%) | 197 (42%) | 269 (58%) |
| **合计** | **387 (43%)** | **221 (24%)** | **302 (33%)** | **608 (67%)** |

VWA 三站合计 **67% 的任务是 visual task**，其中 43% 是显式图片任务，24% 是颜色/外观关键词匹配。

### kwd_only 标记的合理性验证

初看之下，"find the cheapest blue kayak" 这类 `kwd_only` 任务似乎可以纯文本解决——颜色只是筛选条件，标题里应该写着 "Blue Kayak"。但实际实验观察表明，**这些任务在 DOM 模式下同样结构性不可达**，原因有三：

1. **详情页缺乏颜色确认信息**：agent 点进了正确的商品详情页，但 DOM（AXTree）中没有颜色描述文本。agent 无法确认当前商品是否符合颜色要求，认为"不是白色车"而退出，陷入无效循环
2. **商品标题不含颜色关键词**：卖家发布时写的是 "Toyota Camry 2019" 而非 "White Toyota Camry 2019"，颜色信息只存在于商品图片中。DOM 的 AXTree 里完全没有颜色线索，agent 在列表页就无法选中正确的商品
3. **站内搜索匹配失败**：agent 几乎必然会搜索 "white car" 这样包含颜色的具体搜索词，但站内搜索基于标题关键词匹配——标题里没有 "white"，搜索结果为零，任务从搜索阶段就直接卡死

这三个机制说明：**在 classifieds/shopping 类电商站上，颜色等视觉属性在结构化数据（标题、描述、DOM）中是系统性缺失的，只存在于商品图片里**。因此 `kwd_only` 标记没有过度，当前的 visual FP 检测逻辑是准确的。

### VWA Benchmark 的视觉偏重与现实场景的差异

VWA 67% visual task 比例显著高于真实 Web 使用场景。现实中大量 Web 任务是纯文本的（搜索信息、填写表单、阅读文档、管理账户等），真正需要图片理解的任务占比远低于 67%。这意味着：
- VWA 上 DOM 模式的劣势被 benchmark 设计放大了
- 现实场景中 DOM→SoM/Vision routing 的适用范围比 VWA 数据展示的更大
- 论文中应分开报告 visual vs non-visual 任务子集的 routing 效果，说明 routing 价值集中在非视觉任务上

### 实现

在 `analyze_cross_representation.py` 中新增 `_mark_visual_false_positives()` 函数，在 `build_task_pivot()` 后调用：

1. 对 pivot 表每行标记 `is_visual_task` 列
2. 对每个 mode 生成 `{mode}_visual_fp`（仅 DOM 为 True）和 `{mode}_success_adj` 列
3. 所有分析模块（A2/A3/A5/R3）同时输出 raw 和 adjusted 两套指标

具体输出变化：
- **A1**：CSV 含 `is_visual_task`, `dom_visual_fp`, `dom_success_adj` 新列
- **A2**：summary JSON 所有指标增加 `_adjusted` 后缀版本 + `visual_fp_count`
- **A3**：新增 `A3_exclusive_sets_summary_adjusted.csv` 和 `A3_exclusive_sets_detail_adjusted.csv`
- **A5**：CSV 中每个 mode 增加 `_success_count_adj` 和 `_sr_adj` 列
- **R3**：新增 `R3_oracle_decomposition_adjusted.csv`

### Classifieds 站验证结果

```
Visual FP: 162 visual tasks, 19 false positives {'dom': 19, 'som': 0}

A2: union=12.4%, best_single=dom@9.0%, headroom=3.4%
A2 (adj): union=4.7%, best_single=som@4.3%, headroom=0.4%

A3 raw:      all_fail=205, only_dom=19, only_som=8, all_success=2
A3 adjusted: all_fail=223, only_som=9, all_success=1, only_dom=1

R3 raw: 29 union tasks, oracle: {som:9, dom:20}
R3 adj: 11 union tasks, oracle: {som:9, dom:2}
```

### 关键发现

1. **DOM 真实 SR 仅 0.85%**：21 个成功中只有 2 个是非视觉任务的真实成功，DOM 在 classifieds 站上几乎无效
2. **SoM 是实际最强模式**：adjusted 后 SoM（4.3%）> DOM（0.85%），与 raw 数据中 DOM（9.0%）> SoM（4.3%）完全反转
3. **Routing headroom 大幅缩水**：从 3.4% 降至 0.4%，说明 DOM→SoM 切换的收益空间极小——几乎所有 SoM 能解决的任务 DOM 也解决不了（反之亦然）
4. **only_dom 集几乎消失**：从 19 → 1，DOM 独占的成功几乎全是假阳性。仅剩 1 个真实 DOM 独占成功说明 DOM 在 classifieds 站对 SoM 没有互补价值
5. **162/234（69%）的 classifieds 任务是 visual task**：这解释了为什么 DOM 模式结构性劣势如此严重

## 22. 远程开发环境连接配置（2026-04-09） [infra]

### 当前 GPU：DGX Spark (`spark-9ea3`)

通过 Cloudflare Tunnel 连接，本地 SSH config（`C:\Users\Administrator\.ssh\config`）：

```
Host spark
    HostName ssh.holisticai-lab.cc
    User jiaming
    ProxyCommand "C:/Users/Administrator/bin/cloudflared.exe" access ssh --hostname %h
    IdentityFile C:/Users/Administrator/.ssh/id_ed25519_spark
    IdentitiesOnly yes
    PreferredAuthentications publickey,password
    ServerAliveInterval 60
    ServerAliveCountMax 3
    LocalForward 8765 localhost:8765
```

- **ProxyCommand**：通过 `cloudflared` 走 Cloudflare Access 隧道，不直接暴露 SSH 端口
- **LocalForward 8765**：自动转发 gallery HTTP server，本地访问 `http://localhost:8765/gallery.html`
- **publickey 认证**：DGX 上 `~/.ssh/authorized_keys` 已配好，连接不需要输密码。注意 Windows PowerShell 复制公钥时容易带 BOM 字符（`\xEF\xBB\xBF`），需用 `sed -i 's/\xEF\xBB\xBF//g'` 清理

### 已知限制

- **Cloudflare tunnel session 过期**：长时间不操作后隧道会断，VS Code 需要重连（但 publickey 免密，重连无感）

## 23. DOM vs SoM 差距根因修正（2026-04-10） [finding]

### 背景

B1 Classifieds DOM adjusted SR = 0.9%，SoM SR ≈ 19.8%（96 episodes 完成时），差距巨大。需要准确归因 SoM 的优势来源，以指导 Phase 2 路由设计。

### 错误假设的纠正

最初提出三个假设解释 SoM >> DOM，经实证验证后其中两个被推翻：

| 假设 | 结论 | 证据 |
|------|------|------|
| ~~文本压缩 10-20x~~ | **错误** | 实际 DOM = 2326 chars vs SoM = 2377 chars（task_0 step_000 artifacts），内容完全一致，仅格式不同（缩进树 vs `[id=N]` 扁平列表） |
| ~~Coordinate fallback 兜底~~ | **非主因** | SoM 模式碰到下拉菜单交互同样全部陷入循环，坐标兜底在实际中未被有效利用 |
| **Mirage Effect** | **确认为主因** | 与 §18 分析一致：图片存在触发不同推理路径，模型行为模式质变（scroll up 从 DOM 3.7% 提升至 SoM 11.2%，回退策略更丰富） |

### Prompt 差异与公平性

三模式 prompt 的关键差异：

```
DOM:  "ALWAYS use element_id. Do NOT guess coordinates."
SoM:  "Prefer element_id. Use coordinate only when the target is visible
       in the image but has no ID in [SOM_MARKS]."
      + Click by coordinate (fallback) action
```

**结论：当前设计公平。** 理由：

1. **Phase 1 是配置筛选，不是单变量消融** — 每个模式是完整的"配置包"（文本格式 + 适配 prompt + 图片），目的是筛选最优配置往 Phase 2 带
2. **Prompt 差异是功能必需** — DOM 没有图片，给坐标动作没有意义；SoM 有图片，自然需要坐标 fallback
3. **变量隔离由 Phantom-SoM ablation 负责**（§18 已规划）：
   - Phantom-SoM（SoM prompt + SoM text + 无图）vs DOM → 隔离 prompt/格式 的贡献
   - Phantom-SoM vs Full SoM → 隔离图片的贡献

### 修正后的因果模型

```
DOM 模式                          SoM 模式
  AXTree 文本 ≈ SOM_MARKS 文本     (文本信息量相同)
  无图片                            有截图（带标注）
  "你只有文本"                      "你有文本+图片"
       ↓                               ↓
  Guess-mode 推理                   Mirage-mode 推理
  (保守、纯文本先验)                (激活隐藏的文本-视觉关联)
       ↓                               ↓
  SR = 0.9% (adjusted)             SR ≈ 19.8%
```

SoM 的优势**几乎完全来自 Mirage Effect**：相同的文本信息，仅因图片存在（以及暗示图片存在的 prompt 结构），模型进入了质变的推理路径。

### 对 Phase 2 路由设计的影响

- DOM ↔ SoM 路由无意义：routing headroom (adjusted) = 0.4%，DOM 独占成功仅 1 个 task
- 有意义的路由方向：Phantom-SoM ↔ Full SoM（成本差在图片，推理路径可能相近）
- Phantom-SoM ablation 优先级提升：不仅是机制验证，更是 Phase 2 路由可行性的前置实验

## 25. Phantom-SoM Ablation：混淆变量分析与消融设计（2026-04-10） [literature]

### 问题

§18 提出的 Phantom-SoM（SoM marks 文本 + 无图）效果，如果存在，无法直接归因于 mirage effect。DOM 和 SoM 之间存在**三层混淆变量**：

| 层 | DOM | SoM / Phantom-SoM | 差异性质 |
|---|---|---|---|
| ① **Prompt** | "Use element IDs from Accessibility Tree"，无坐标 action | "You receive [SOM_MARKS] + screenshot"，含坐标 fallback schema | Action space 扩大 |
| ② **文本格式** | `Accessibility Tree:\n` + 完整 AXTree | `[SOM_MARKS]...[/SOM_MARKS]` 标注块 | 信息编码方式不同 |
| ③ **图片暗示** | Prompt 未提及图片 | Prompt 明确说"A screenshot — normally with bounding boxes" | Mirage trigger |

直接对比 Phantom-SoM vs DOM 是 ①+②+③ 的混合效应，无法分离 mirage effect 的真实贡献。

### Prompt 差异的具体影响

**坐标 fallback 是最大的混淆因素：**

- DOM prompt（line 139）：`ALWAYS prefer element_id. Only use coordinate as last resort.` 但 action schema 中**没有给坐标格式**，模型事实上无法输出坐标动作
- SoM prompt（line 200-201）：`Click by coordinate (fallback): {"action_type": "click", "coordinate": [x, y], "coordinate_type": "normalized"}` 明确给出了坐标 action schema
- 这意味着 SoM 模式下模型在 element_id 匹配不上时有**额外操作通路**——这是纯 action space 差异，与 mirage 无关

**文本格式的潜在影响：**

- AXTree 是层级缩进结构，包含所有节点（含不可交互节点）
- SoM marks 是扁平列表，只包含可交互元素 + 短描述
- 虽然 §23 已确认 token 量级相当（DOM 2326 ≈ SoM 2377 chars），但信息密度和结构不同，可能激活不同的 pretrain 知识路径

### 消融矩阵设计

| 组 | Prompt | 文本内容 | 图片 | 隔离目标 |
|---|---|---|---|---|
| **A: DOM baseline** | DOM prompt | AXTree | 无 | 基准 |
| **B: Phantom-SoM** | SoM prompt | SoM marks | 无 | ①+②+③ 混合（原计划） |
| **C: Full SoM** | SoM prompt | SoM marks | 有 | ③→真实视觉 vs B |
| **D: DOM-text + SoM-prompt** | **SoM prompt** | **AXTree** | 无 | 纯 ① prompt 效应 |
| **E: SoM-text + DOM-prompt** | **DOM prompt** | **SoM marks** | 无 | 纯 ② 格式效应 |

**因果分解：**

- `B - A` = prompt + 格式 + mirage 混合效应
- `D - A` = 纯 prompt 效应（坐标 fallback action space 的贡献）
- `E - A` = 纯文本格式效应（SoM marks vs AXTree 的信息结构差异）
- `B - D` = 在 SoM prompt 下，SoM marks 相对 AXTree 的增量贡献（② given ①）
- `B - E` = 在 SoM marks 下，SoM prompt 相对 DOM prompt 的增量贡献（① given ②）
- `C - B` = 纯图片贡献（真正的 mirage isolation：声称有图 vs 真的有图）

### 实验 D 详细设计：DOM-text + SoM-prompt

**目的：** 隔离 SoM prompt 中坐标 fallback action space 对性能的影响。如果 D ≈ B，说明 prompt（坐标 fallback）才是主因，mirage effect 不成立。

**实现方式：**
- 使用 `_make_som_prompt()` 生成的 system prompt（含坐标 fallback schema、"screenshot" 提及）
- 文本观测使用 DOM 模式的 AXTree（`Accessibility Tree:\n` + obs_text）
- 不传入图片
- 需要在 `qwen3vl_agent.py` 中新增 `observation_mode="phantom_dom"` 分支，或在 runner 层做 prompt/obs 组合覆盖

**预期结果与解读：**
- `D ≈ A`：坐标 fallback 无用（模型没有图就不会用坐标），prompt 差异不是主因
- `D > A`：坐标 fallback 偶尔命中（随机坐标点击到目标），或 prompt 中"screenshot"暗示激活了 mirage
- `D ≈ B`：SoM marks 文本格式没有额外贡献，全部效果来自 prompt

### 实验 E 详细设计：SoM-text + DOM-prompt

**目的：** 隔离 SoM marks 文本格式对推理质量的影响。SoM marks 是可交互元素的扁平列表，比 AXTree 更聚焦——这种信息结构差异可能本身就足以改善决策质量，无需 mirage effect。

**实现方式：**
- 使用 `_make_dom_prompt()` 生成的 system prompt（无坐标 fallback、无 screenshot 提及）
- 文本观测使用 SoM 标注块（`[SOM_MARKS]...[/SOM_MARKS]`）
- 不传入图片
- prompt 中 element_id 引用仍然有效（SoM marks 也用 `[id=N]` 格式）
- 需要调整 prompt 中 "Accessibility Tree" 的措辞为更通用的描述，或保持原样（模型应能理解列表格式）

**预期结果与解读：**
- `E ≈ A`：SoM marks 格式本身无优势，信息内容等价
- `E > A`：扁平列表（只含可交互元素）比层级 AXTree（含全部节点）更利于 4B 模型决策——信息过滤/压缩有贡献
- `E ≈ B`：prompt 差异（坐标 fallback）没有额外贡献，全部效果来自文本格式

### 文献综述关键发现（2026-04-10，详见 `docs/literature/phantom_som.md`）

基于 SciSpace 深度调研（43 篇论文，6 个主题），以下发现直接影响消融设计：

#### Scaffold Effect：最大威胁

Vu & Balloccu (2026, [19]) 发现**仅在 prompt 中提及 "MRI 可用" 就能解释 70-80% 的表观性能变化**，与实际是否传入图片无关。这直接命中 Phantom-SoM 场景——SoM prompt 写了 "You receive a screenshot with bounding boxes"，这句话本身可能就是 Phantom-SoM 效果的主要驱动力，而非 mirage effect。

**→ 实验 D 变成了整个消融中最关键的判别组：它同时包含 scaffold（prompt 提及截图）和 action space（坐标 fallback），如果 D ≈ B，则 SoM marks 文本格式无额外贡献，效果全部来自 prompt 层。**

#### 额外混淆因素确认

| 混淆源 | 文献支撑 | 影响 |
|--------|----------|------|
| **Element ordering** | Chi et al. [17]：随机化元素顺序的性能下降**等同于删除可见文本** | AXTree 层级 vs SoM marks 扁平列表的排序差异是独立混淆因素 |
| **Action space** | Szot et al. [15]：action adapter 选择**显著改变** agent 性能和 grounding 保真度 | 坐标 fallback vs element-ID 是独立于观测模式的性能驱动力 |
| **Prompt framing** | Verma et al. [14]：ReAct prompting 的表观增益主要来自 exemplar-query 相似度，非推理链本身 | 需要控制 prompt 中与观测模式无关的措辞差异 |

#### 文献空白 → P79 novelty

综述确认 6 个 gap，其中 3 个直接对应 P79 贡献：

1. **Gap: Intra-model observation-mode routing** — 无人做过同一 VLM 内切换观测模式（DOM/SoM/Vision）的路由研究。现有 cascading 全是 inter-model（小模型→大模型）。P79 是第一个。
2. **Gap: 系统性四因素消融** — 无人同时消融 prompt + 格式 + action space + modality。个别因素有独立研究，但无 factorial design 覆盖全部。5 组设计填补此空白。
3. **Gap: 把 mirage effect 当 feature** — 现有文献全部把 text-over-vision bias 当 bug 来修（M3ID [5]、attention amplification [6]、VA-neuron detection [2]）。P79 反其道而行之，利用 bias 省成本。

#### 路由信号候选

| 信号 | 来源 | 成本 | 与 P79 关系 |
|------|------|------|------------|
| Linear probes on mid-layer activations | Pacchiardi [37]：中间层线性探针预测答案正确性 | 零（forward pass 内） | 需要白盒访问，4B 本地模型满足 |
| BrowseConf verbalized confidence | Ou et al. [35]：web agent 的 verbalized confidence 与准确率强相关 | 零（已在输出中） | B1 token-level AUROC=0.497 已失败，verbalized 是否不同待验证 |
| WebArbiter step-level PRM | Zhang et al. [29]：step-level 过程奖励模型 | 高（7B verifier） | 4B actor 旁跑 7B 太贵，不适合 B1 |
| VA-neuron detection | Kim et al. [2]：检测视觉缺失 token | 低（探针） | 可作为 Phantom-SoM → Full SoM 升级信号 |

#### Task 54 案例佐证

SoM 模式下 task 54（"Find the most recently listed item related to this game I used to play"，带参考游戏截图）的 30 步 trajectory 证实了 text-over-vision bias：

- 模型知道有图（Step 13/17/19 提到 "as seen in the screenshot of the game"）
- 但**从未识别出图片中的游戏名称**，无法用图片内容做匹配
- 决策完全靠文本线索（"Newly listed" 排序→选第一个），图片形同虚设
- 陷入 item 详情页↔列表页的死循环（30 步中 20+ 步重复相同模式）

这是 4B 模型 text-over-vision bias 在参考图场景下的直接体现，支撑 Phantom-SoM（无图）与 Full SoM（有图）对 4B 效果接近的假设。

### 样本量修正

文献建议 n ≥ 200/组（1000 total）检测 Cohen's d ≈ 0.3 的小效应（[19] scaffold effect 分析）。原计划 50/组不足。

**修正方案：复用 B1 baseline 数据 + 自适应停止。**

- **A 组**：复用 B1 DOM baseline 全部 234 tasks（不需重跑）
- **C 组**：复用 B1 SoM baseline（目前 135 tasks 已完成，最终 ~234 tasks）
- **B/D/E 组**：使用与 A/C 相同的 task set，确保 paired comparison
- 实际新增工作量：B + D（+ 可能的 E）= 234×2 ~ 234×3 = **468-702 tasks**

**paired design 优势**：同一 task 跨组配对比较，所需样本量大幅下降（paired t-test 控制 task 内变异），234 tasks 的 paired comparison 统计功效远优于 200 tasks 的 independent comparison。

**统计方法**：
- 主要分析：McNemar's test（paired binary outcomes）或 paired permutation test
- 多重比较校正：Benjamini-Hochberg FDR（q=0.05），10 个 pairwise comparison
- 报告：uncorrected + FDR-corrected p-values + Cohen's d + 95% CI

### 决策树（修正版）

```
Phase 1: 跑 B + D（各 234 tasks，与 A/C paired）
         ↓
D ≈ B ?  （McNemar test, FDR-corrected）
├── YES → 结论：prompt/action-space 是主因（scaffold effect 确认）。
│         Phantom-SoM 效果 = prompt 效应，非 mirage。
│         → 无需跑 E，但发现本身有价值（scaffold effect 在 web agent 中的首次量化）
│
└── NO → D ≈ A ?
    ├── YES → prompt 无贡献。跑 E 分离格式 vs mirage。
    │         E ≈ B → 格式是主因（SoM marks 信息过滤/压缩的贡献）
    │         E ≈ A → mirage 是主因（prompt 暗示图片存在触发推理路径变化）
    │
    └── MIDDLE → prompt 有部分贡献（D 显著优于 A 但劣于 B）。
                 跑 E 做三方分解：效应 = prompt_share + format_share + mirage_share
```

### 实现注意事项

1. **A 组不需重跑**：直接复用 B1 DOM baseline 数据
2. **C 组不需重跑**：直接复用 B1 SoM baseline 数据
3. **B/D/E 使用相同 task set**：与 A/C 完全 paired，消除 task 难度变异
4. 需要在 agent 或 runner 层支持 prompt/observation 的交叉组合，当前代码 observation_mode 是一个原子选择，需要解耦
5. **Element ordering 控制**：E 组的 SoM marks 喂给 DOM prompt 时需保持与 B 组相同的元素排序策略，避免引入新混淆（[17]）
6. **Scaffold 控制组（可选）**：如果资源允许，增加 D' 组——SoM prompt **去掉 "screenshot" 提及** + AXTree + 无图——进一步分离 scaffold effect 和 action space effect

## 28. Vision 模式 type 动作 bug 修复（2026-04-11） [bug]

### 问题

Vision 模式下 agent **完全无法 type**。Agent prompt 正确指示模型使用 coordinate 指定目标输入框：

```json
{"action_type": "type", "text": "query", "coordinate": [0.5, 0.4], "coordinate_type": "normalized"}
```

但 `vwa_wrapper.py:181-183` 收到该 action 后，因 `element_id not in action_json`，直接走 `create_keyboard_type_action(text)` —— **丢弃了 coordinate 字段**，文本被输入到当前聚焦元素（通常为空），等同于 type 失败。

对比：
- DOM/SoM 模式：type 使用 `element_id`，VWA 自动定位并聚焦 → 正常
- Vision 模式：type 使用 `coordinate`，wrapper 未处理 → 失败

### 修复

`vwa_wrapper.py` L181-195：当 type 包含 coordinate 但无 element_id 时，先用 coordinate 执行一次 `_env.step(click_action)` 聚焦目标输入框，再执行 `keyboard_type_action`。坐标处理逻辑（归一化、像素转换、eps clamp）复用 click coordinate 分支。

```python
elif action_type == "type" and "text" in action_json and "element_id" not in action_json:
    coord = action_json.get("coordinate")
    if coord is not None and isinstance(coord, (list, tuple)) and len(coord) == 2:
        left, top = float(coord[0]), float(coord[1])
        if left > 1.0 or top > 1.0:
            left /= float(self.viewport_width)
            top /= float(self.viewport_height)
        eps = 1e-6
        left = max(eps, min(1.0 - eps, left))
        top = max(eps, min(1.0 - eps, top))
        click_action = create_mouse_click_action(left=left, top=top)
        self._env.step(click_action)  # focus the target input
    action = create_keyboard_type_action(action_json["text"])
```

### Latency 影响

额外 click 增加 ~几十ms 浏览器操作时间，计入该 step 的 wall time，但不产生额外 token 消耗，不记录为独立 step。属于功能必需开销。

### 处置

已用 `clear_tasks.py --force` 删除修复前跑出的 3 个 vision task（task 0/1/2）及对应 digest 记录，runner 会自动重跑。

## 29. Vision 模式 CDP 焦点丢失 bug：pre-click 机制根因修复（2026-04-11） [bug]

### 背景

§28 的修复（pre-click 聚焦 + keyboard.type）上线后，Vision 实验已跑完 191 个 episode（SR 3.16%）。但分析发现 **step 0 的 type 操作 0/68 成功提交搜索表单**，尽管坐标准确命中搜索框（Playwright 复刻验证坐标正确，INPUT#query 的 bounding rect 包含目标点）。

初始分析方向（模型 grounding 精度不足、autocomplete 拦截 Enter 等）均被排除。

### 根因定位

通过 Playwright 对照实验精确定位：

| 测试 | 操作 | 结果 |
|------|------|------|
| 直接 `page.mouse.click()` + `page.keyboard.type()` | 不经过 VWA | ✓ 搜索提交，URL 变化 |
| VWA `env.step(click)` + VWA `env.step(type)` | 经过 VWA | ✗ URL 不变 |
| VWA `env.step(click)` + 直接 `page.keyboard.type()` | click 经过 VWA | ✗ URL 不变 |

**关键对比**：直接 click 后 `document.activeElement` = `INPUT#query`；VWA `env.step(click)` 后 `document.activeElement` = `BODY`。

**根因**：VWA 的 `ScriptBrowserEnv.step()` 在每次 action 执行后调用 `_get_obs()` 捕获观测，其中 CDP（Chrome DevTools Protocol）`DOMSnapshot.captureSnapshot` 调用会**重置页面焦点**，将 INPUT 焦点移到 BODY。

§28 的代码用 `self._env.step(click_action)` 做 pre-click，触发了完整的"click → sleep → CDP 观测捕获"流程。CDP 捕获把刚聚焦的 INPUT 吹掉后，后续 `keyboard.type()` 的文本被输入到 BODY（空操作），等同于 type 失败。

### 修复

`vwa_wrapper.py` L184-199：pre-click 改为直接调用 `page.mouse.click()` + `page.wait_for_timeout()`，绕过 VWA 的 `env.step()` 和 CDP 观测捕获，保持 INPUT 焦点：

```python
# 修复前（焦点被 CDP 吹掉）：
click_action = create_mouse_click_action(left=left, top=top)
self._env.step(click_action)

# 修复后（直接 click，跳过 CDP 观测捕获）：
self._env.page.mouse.click(
    left * self.viewport_width,
    top * self.viewport_height,
)
self._env.page.wait_for_timeout(int(self.sleep_after_execution * 1000))
```

同时修复了 §28 遗留的混合坐标 bug：`if left > 1.0 or top > 1.0` 改为独立判断 `if left > 1.0` / `if top > 1.0`，避免一个维度是归一化另一个是像素值时的错误缩放。

### 验证

修复后用 VWAWrapper 直接测试：
- Multi-word `"blue kayak\n"` → ✓ URL 变为 `?page=search&sPattern=blue+kayak`
- Single-word `"bike\n"` → ✓ URL 变为 `?page=search&sPattern=bike`

### 影响评估

- **Type 操作**：修复前 step 0 成功率 0/68 (0%)，修复后预期接近 100%
- **Click 操作**：不受此 bug 影响（click 不需要 pre-click + keyboard.type 两步）
- **DOM/SoM 模式**：不受影响（使用 element_id 的 id-based typing，不经过 pre-click 路径）

### 处置

**Vision 实验需要全部重跑**。现有 191 个 episode 的 type 操作全部受到 CDP 焦点丢失影响，3.16% 的 SR 低估了模型在坐标型交互下的真实能力。

### 背景

§29 修复了 type 的 CDP 焦点丢失后，继续排查 Vision 模式 click 失效问题。task 2 step 3 中 agent 点击 Jewelry 分类链接（坐标精准命中 `<a>` 标签），但 URL 不变。

### 根因定位

通过 5×3 对照实验精确定位：

| 测试 | 方式 | 5 次结果 |
|------|------|----------|
| A | `create_id_based_action("click [946]")` → env.step | 5/5 导航成功 |

- **id-based 路径**：参数类型为 Python `float`，1 次调用 → 成功
- **coordinate 路径**：参数类型为 `numpy.float32`，2 次调用 → 失败

进一步验证：

```python
# VWA create_mouse_click_action 强制 float32：

json.dumps(float(470.0))       → OK
```

1. VWA `create_mouse_click_action` 存坐标为 `np.float32`
2. NumPy 2.x 类型提升：`float32 × int → float32`（旧版→float64）

## 31. click vs type 混淆与 baseline retry 副作用（2026-04-11） [finding][bug]

### 问题发现

Vision B1 前 18 task 分析中发现 agent 在需要向输入框填写内容时（如价格筛选），使用 `click` 而非 `type` action。

**Task 7 step 4**（价格筛选）：agent thought "需要应用 $300-600 价格筛选"，生成 `click [0.168, 0.578]`。click 可能聚焦了输入框（光标闪烁），但 DOM 变化太小，`detect_page_state_change` 判定 `page_changed=false`。Runner 触发 baseline retry scroll，把已聚焦的输入框滚出视野。Agent 下一步看到 scroll 后的新画面，丢失了输入意图。

**三模式共性**：SoM digest 记录了相同缺陷（task_19 正确定位 Min 价格 textbox eid=2596 但用 click 而非 type）。DOM digest 4.3.4 也有价格输入框操作失败。SoM 模式偶尔成功使用 type（有 AXTree 标注 textbox 辅助判断），DOM/Vision 基本不会。

### 根因分析

1. **Prompt 措辞不清晰**：三个模式的 prompt 都只说 type action 的 coordinate "recommended"，没有说明：
   - `type` 会自动 click 聚焦——不需要先 click 再 type
   - 要输入内容**必须用 type**——click 只能聚焦/导航，不能输入
   - click 用于按钮/链接，type 用于输入框

2. **当前架构下"先 click 再 type"的两步策略在结构上不可行**：
   - Click 输入框 → DOM 变化极小 → `page_changed=false`
   - Runner baseline retry 自动注入 scroll → 输入框滚出视野
   - Agent 无跨步意图记忆 → 看到新画面去做别的了
   - 即使没有 retry，agent 下一步也不会自动接 type（每步独立决策，无多步计划持续追踪）

3. **`type` action 的 wrapper 实现已自带完整流程**（`vwa_wrapper.py:183-210`）：
   ```
   type + coordinate → mouse.click(coord) → wait → Meta+A → Backspace → keyboard.type(text)
   ```
   Agent 只需发一个 `type` action 即可一步完成 click→focus→清空→输入。

### baseline_retry_on_no_progress 机制说明

Runner 的 baseline retry（`runner.py:996-1008`）：当 click/type 后 `page_changed=false` 时，自动注入一次 scroll down。

**设计意图**：
- 假设 click 失败是因为目标在视口外，scroll 可暴露目标
- 打破 agent 重复相同 action 的死循环

**副作用**：对输入框聚焦场景有害——click 实际成功了（焦点已获取），但 DOM 变化太小被判为无变化，retry scroll 反而破坏了焦点状态。

### Prompt 修改属于公平性修改

理由：
- 三个模式（DOM/SoM/Vision）的 prompt 需要同样的措辞修改
- 不改变任何模式的结构性优劣势（DOM 仍有 element_id，SoM 仍有标注，Vision 仍只有坐标）
- 只是让 action 语义更清晰，减少 4B 模型的指令理解歧义
- 类比：EIP 站点先验也是注入 prompt 的公平性增强

**建议修改方向**（待 B1 全站跑完后统一实施）：
```
Type: {"action_type": "type", "text": "string", ...}
  - This action automatically clicks the target location to focus it before typing.
  - ALWAYS use "type" (not "click") when you want to enter text into an input field.
  - "click" is for buttons, links, and navigation only.
```

### 跨步意图记忆缺失

当前 agent 每步独立决策，唯一的跨步信息来自 `_format_history()`：
```
Previous actions:
  Step N: click coord=[x,y] -> OK (page unchanged) [url]
```

这只记录"做了什么→结果如何"，不包含意图（"我正在做价格筛选的第 1/3 步"）。M4 `two_stage_generation_grounding` 是单步内的 planner→grounder 拆分，不是跨步计划追踪。

### baseline_retry_on_no_progress 全面评估

Click/type 后 `page_changed=false` 时，runner 自动注入一次 scroll down（`m3_retry_action`，delta=[0, 0.5]）。Retry 不消耗 step 预算但真实改变环境状态。

#### 定量数据

**Retry 触发率与"成功率"**：

| 模式 | Retry 触发率 | Retry 后 page_changed=true |
|------|-------------|--------------------------|
| DOM | 6.7%（235/3495 步） | **100%** |
| SoM | 9.7%（270/2760 步） | **100%** |
| Vision | 9.6%（27/280 步） | **100%** |

100% 的 retry scroll 都导致 page_changed=true——scroll 几乎必然改变页面内容，所以 retry 的"成功"无信息量。

**对成功 episode 的影响**：

| 模式 | 成功+有 retry | 成功+无 retry | retry 后切换 element |
|------|-------------|-------------|-------------------|
| DOM | 6 | 15 | 89%（8/9 次） |
| SoM | 24 | 24 | 95%（20/21 次） |
| Vision | 2 | 2 | — |

Retry 后 89-95% 切换到不同 element，但 agent 自己也会 scroll——retry 只是提前一步做了 agent 本来会做的事。

**对失败 episode 的影响（步数浪费）**：

| 模式 | 失败+有 retry 平均步数 | 失败+无 retry 平均步数 | 差值 |
|------|---------------------|---------------------|------|
| DOM | 19.8 | 11.4 | **+8.4 步** |
| SoM | 16.7 | 8.6 | **+8.1 步** |
| Vision | 8.2 | 5.4 | **+2.8 步** |

有 retry 的失败 episode 平均多浪费 8 步——因为 retry scroll 的 page_changed=true 清空了 soft cycle signatures（runner.py:1249-1252），**阻止了早停机制触发**。

#### 五个问题

1. **100% 假阳性**：retry scroll 总是"成功"（页面总会变），没有信息量
2. **破坏 cycle detection**：retry 的 page_changed=true 清空 soft signatures，绕过已有早停机制，导致失败 episode 多浪费 ~8 步
3. **三模式不公平**：DOM/SoM scroll 后仍有 element_id 精确定位，Vision scroll 后坐标全部失效；Vision retry 率（9.6%）与 SoM 相当但伤害更大
4. **破坏焦点**（§31 主体已分析）：click 成功聚焦输入框 → 判为 page_unchanged → retry scroll 破坏焦点
5. ~~**抢走重试机会**~~（已修正）：实际观察（如 task 48）表明模型**不具备跨步自纠正能力**——misclick 后 agent 会以相同坐标、相同 confidence 重复点击（无意图记忆），并不会微调坐标。因此 auto-scroll 不存在"抢走重试机会"的问题，它只影响效率（多浪费步数），不影响 SR

#### 对成功率的影响预估

| 模式 | 当前 SR | 去掉 retry 预估 | 理由 |
|------|--------|---------------|------|
| DOM | 8.97% | ~8.5%（-1 ep） | 可能丢 1 个 retry 恰好暴露关键元素的边缘 case |
| SoM | 20.51% | ~19.7%（-1~2 ep） | 同上 |
| Vision | ~9% | ~9%（不变） | 模型无跨步自纠正能力（task 48 验证），去掉 auto-scroll 不会帮助 misclick 重试 |

**SR 影响极小（±1-2 episode），Vision 模式为零影响**。主要收益是效率：失败 episode 更快触发早停，减少 ~8 步无效推理 → 降低成本。

> **修正说明**（2026-04-12）：早期分析认为 auto-scroll "抢走 Vision 重试机会"，去掉后 Vision SR 可能略升。Task 48 实际轨迹否定了这一假设——agent 在 step 7-10 以完全相同的坐标 [0.49, 0.44] 连续点击 4 次（confidence 均为 0.95），无任何自我纠正迹象。这是 F1（stuck-in-loop）模式的典型表现：模型缺乏跨步意图记忆，misclick 后只会重复而非调整。因此 auto-scroll 的影响纯粹是效率层面，不涉及 SR。

#### 结论

**建议在最终 baseline 重跑时关闭 `baseline_retry_on_no_progress`**：
- 与已有早停机制功能重叠，且实际上破坏了 soft cycle 检测
- 三模式受影响程度不同，引入系统性不公平
- 对 SR 影响极小（DOM/SoM ±1-2 ep，Vision 零影响——模型无跨步自纠正能力）
- 主要收益：减少失败步数浪费（~8 步/episode）→ 降低成本
- 作为 agent 未请求的隐式干预，不符合 baseline "最小干预"原则
- M3 模块（Phase 3 消融对象）保持独立，不受影响

### auto-scroll 与 `<select>` 脚手架缺陷的交互（Task 19 case study）

Vision task 19（找 Arts + crafts 分类中 $80-100 的海景画）暴露了 auto-scroll 与 `<select>` 下拉菜单缺陷（`B1_findings.md` §6.3）的意外交互。

**轨迹还原**：

| Step | Action | page_changed | retry_applied | 实际效果 |
|------|--------|-------------|---------------|---------|
| 0 | click [0.598, 0.418] | true（title_changed） | 否 | 打开分类 `<select>` 下拉菜单 |
| 1 | click [0.554, 0.138] "Arts + crafts" | **false → retry scroll** | **是** | 点击 option 无效（§3 第一层），retry scroll 关闭了下拉菜单（modal_state_changed），页面大幅变化（text_sim=0.12） |
| 2 | click [0.192, 0.904] | false → retry scroll | 是 | 再次 click 失败，retry scroll 继续改变页面 |
| 3 | click [0.362, 0.077] 分类图标 | true（url_changed） | 否 | **成功导航到 Arts + crafts**（sCategory=4） |
| 4-9 | scroll ×6 | true→false | 否 | 浏览 listings → 到底 → page_unchanged_streak → 早停 |

**auto-scroll 的意外正面作用**：
- Step 1 中 agent 点击 `<select>` option 失败（VWA 框架缺陷），auto-scroll 触发
- Scroll 关闭了下拉菜单（浏览器原生行为：页面滚动时 `<select>` dropdown 自动收起）
- Agent 在 step 3 发现了页面上的分类图标链接（替代路径），成功进入目标分类
- **如果没有 auto-scroll**：dropdown 保持打开 → agent 可能连续 3 次点击同一 option（Vision F1 misclick 循环模式）→ page_unchanged_streak → episode 在 step 3 就早停，从未到达目标分类页

**与其他脚手架缺陷的交互**：

| 缺陷（B1_findings.md §6） | auto-scroll 能帮助？ | 原因 |
|----------------------|-------------------|------|
| §3 `<select>` 下拉菜单 | **意外有效** | scroll 关闭 dropdown，迫使 agent 寻找替代路径 |
| §5 不会翻页 | 无帮助 | agent 自己就在 scroll，auto-scroll 只是提前一步做同样的事 |
| §6 confirm 弹窗 | 无帮助 | scroll 不影响浏览器原生 confirm() 对话框 |
| §1 地点过滤 | 无关 | 搜索框无法按地点过滤，与 scroll 无关 |
| §2 编辑页字段不可达 | 理论上可能 | 但 scroll 方向/量是固定的（[0, 0.5]），命中目标字段是偶然 |

**如果去掉 auto-scroll，`<select>` 场景怎么办？**

不去掉 auto-scroll 时：agent 在 1 步后脱离 dropdown → 3 步后找到替代路径（步数开销 4）。

去掉后：agent 连续 3 次 click option → page_unchanged_streak → 早停。但这反映了真实的脚手架缺陷暴露——`<select>` 确实不可用，auto-scroll 只是掩盖了问题。更好的解决方案是 M1 select fallback（Phase 3 消融对象），而非依赖 auto-scroll 的副作用。

**结论**：auto-scroll 对 `<select>` 缺陷有意外的逃逸效果，但这是巧合而非设计。去掉 auto-scroll 后，cycle detection 仍然提供等效保护（3 步 vs 1 步，代价是 2 步差异）。此分析进一步支持§31 "关闭 auto-scroll"的建议——不应依赖副作用来处理脚手架缺陷。

## 32. Vision 坐标 Misclick 系统性偏差：Art+crafts → Books（2026-04-12） [finding]

### 发现

Task 100/101/102 均要求导航到 classifieds 站点的 Art+crafts 分类。Vision 模式在三个任务中表现出**完全一致的坐标偏移**：

| Task | 点击坐标 | 实际落点 | 预期落点 |
|------|---------|---------|---------|
| 101 step 3 | `[0.37, 0.15]` | Books (sCategory=9) | Art+crafts (sCategory=4) |
| 101 step 6 | `[0.37, 0.15]` | Books (sCategory=9) | Art+crafts (sCategory=4) |
| 101 step 9 | `[0.37, 0.15]` | Books (sCategory=9) | Art+crafts (sCategory=4) |
| 102 step 3 | `[0.36, 0.15]` | Books (sCategory=9) | Art+crafts (sCategory=4) |

Agent 的 thought 每次都正确提到「导航到 Art+crafts」，但**以完全相同的坐标重复点击**，反复落到相邻的 Books 类目，形成 back→click→back→click 死循环。

### 三模式对比

| 模式 | Art+crafts 导航 | 失败原因 |
|------|----------------|---------|
| DOM | ✓ 通过 element_id 正确进入 sCategory=4 | Visual task，看不到图片 |
| SoM | 混乱（搜索框输入、乱点） | 未有效导航到分类 |
| Vision | ✗ 坐标偏移 → Books | **系统性 misclick** |

DOM 模式通过 AXTree element_id 100% 准确命中 Art+crafts，证明 UI 元素本身没问题。Vision 模式的坐标解码在相邻类目按钮之间发生了系统性偏移。

### 与 §19 Tool Calling 线性电路的关联

这是 §19「模型知道但说不出来」的**坐标参数版**：

| 层级 | 状态 | 说明 |
|------|------|------|
| Thought（推理） | ✓ 正确 | 「导航到 Art+crafts」 |
| Action type 选择 | ✓ 正确 | `click` |
| **Argument 生成（坐标）** | ✗ 偏移 | `[0.37, 0.15]` → Books |

论文框架将 tool calling 分解为两步：action selection（线性、低维可操控）和 argument generation（非线性）。Task 100-102 显示偏差发生在第二步——模型选对了 click，但坐标参数解码有偏。

### 零自纠正验证

三个任务中 agent 在发现点到 Books 后，**以完全相同的坐标重试**而非微调。这与 task_48 的 misclick 行为一致（§31），进一步确认模型缺乏跨步自纠正能力。

### Future Work：离线 Activation 坐标修正

这三个任务是 §19 离线 activation 提取实验的理想测试用例：

1. **Step 1**：取 vision task_101 step 3 的 prompt + 截图，forward pass 提取 L23+ hidden states
2. **Step 2**：检查 attention head 是否 attend 到截图中 Art+crafts 的**正确空间位置**（而非 Books 位置）
3. **Step 3**：若内部表征指向正确位置，说明偏差在坐标解码层——可通过 activation steering 修正
4. **意义**：不只是切换 action type（论文原始场景），而是**在同一 action type 内修正空间参数**，扩展了 steering 方法的应用范围

关键优势：零额外 token 成本、零额外推理调用，只需在 forward pass 中间插入方向向量。仅对 B1（本地白盒）可行，强化了 cost-aware routing 中本地模型的独特价值。

## 36. 参考图标签缺失导致 DOM 模式无法利用参考图（2026-04-12） [bug]

### 36.1 现象

Reddit task 0：intent 是 "I'm trying to find this post"，参考图是一张寿司拼盘照片。AXTree 中有 `[I ate] Sushi platter` 帖子。Agent 收到了参考图（`image_tokens=768`），但 8 步内**从未提及 sushi/image/photo**，thought 说 "the target post is not specified"，盲目点击第一个帖子。

Task 1 类似：thought 说 "The image provided is unrelated to the task"——承认看到了图片，但认为无关。

### 36.2 根因

**三种模式的 system prompt 和参考图标签都未说明参考图的用途。**

模型收到的 content 序列：

```
1. [text] "Task: I'm trying to find this post...\nSystem: ...\nAccessibility Tree: ...(~3800 tokens)"
2. [text] "[Input image 1]"          ← 标签太泛化
3. [image] 🍣 寿司拼盘 (768 tokens)
```

- `"this post"` 出现在开头，图片在末尾，中间隔了几千 tokens 的 AXTree
- `[Input image 1]` 标签没有告诉模型这张图和任务中的 "this" 有关
- System prompt 完全不提参考图的存在

对 4B 模型来说，没有显式指引就不会主动建立"参考图 = 任务目标"的关联。**这不是图片识别能力问题**（模型能识别寿司），而是 prompt 没告诉模型要去看那张图。

### 36.3 修复

**`qwen3vl_agent.py`**：参考图标签从泛化的 `[Input image 1]` 改为显式指引：

```python
# Before
"[Input image 1]"

# After
"[Reference image 1] This image shows the target item described in the task. Use it to identify which element to interact with."
```

### 36.4 验证（A/B 对比，同一 task）

| | 旧标签 `[Input image 1]` | 新标签 `[Reference image 1] This image shows...` |
|---|---|---|
| Step 0 thought | "the target post is not specified" | **"The target image shows a sushi platter, which matches '[I ate] Sushi platter'"** |
| 图片识别 | 8 步从未提到 sushi | **第 1 步就识别出 sushi platter 并匹配到 AXTree 元素** |
| 总步数 | 8 步（循环点击，无法定位） | **2 步**（直接匹配 + 点击 comments） |

### 36.5 影响范围

- **三种模式共用同一段参考图注入代码**，标签修复对 DOM/SoM/Vision 都生效
- SoM/Vision 本来就能通过视觉对比理解参考图，新标签不会有副作用，可能有微小正向收益（减少参考图 vs 截图的歧义）
- Reddit 84/210 tasks（40%）有参考图，Classifieds ~30% 有参考图，Shopping 待查
- Classifieds 旧数据已丢需重跑，三站统一用新标签，无一致性问题

## 39. B0 三模式启动中的三类 Bug（2026-04-13） [bug][infra]

B0 classifieds 三模式（`run_b0_3mode_classifieds.sh`）首次完整启动后，暴露出三个独立但相互叠加的问题，导致大量数据污染。以下按发现顺序记录。

### 39.1 Bug A：Classifieds Osclass Error（Docker MySQL 初始化顺序 bug）

**现象**：B0 DOM condition 跑出 219 个 episodes 后，gallery 显示所有 task 截图都是 Osclass 安装页（"Osclass isn't installed"），站点从一开始就处于损坏状态。

**根本原因**：Docker MySQL 容器的 `/docker-entrypoint-initdb.d/` 目录下有三个脚本，按**字母序**执行：

```
c - classifieds_restore.sql   ← 仅含数据（依赖 schema 已存在）
i - init_db.sh               ← 创建 schema + 插入初始数据
o - osclass_craigslist.sql   ← Osclass 基础数据
```

`classifieds_restore.sql`（c）在 `init_db.sh`（i）之前运行，因 schema 不存在而报错 → MySQL 在 `init_db.sh` 未运行的情况下退出初始化流程 → 数据库只有空库 → Osclass 检测到空库显示安装页。

**影响**：219 个 DOM episodes 全部是在损坏站点上运行的，全部无效。

**修复**：
1. **立即修复（当次实验）**：手动执行 `docker exec classifieds_db bash /docker-entrypoint-initdb.d/init_db.sh`，站点恢复正常。
2. **永久修复**：在 `reset_vwa.ps1` 的 90s 等待后追加：
   ```powershell
   if ($Site -eq "classifieds" -or $Site -eq "all") {
       Write-Host "[reset] initializing classifieds DB (init_db.sh)..."
       docker exec classifieds_db bash /docker-entrypoint-initdb.d/init_db.sh
       Write-Host "[reset] classifieds DB init done"
   }
   ```

**教训**：classifieds 每次 reset 后都需要手动触发 `init_db.sh`，否则站点将以空库启动。此后每次 reset 均通过 `reset_vwa.ps1` 自动执行此步骤。

### 39.2 Bug B：PHP session 过期导致大规模数据污染（gc_maxlifetime=1440s）

**现象**：B0 SOM 开始后 watchdog 持续上报：
```
[watchdog][SESSION] classifieds task 32 NOT LOGGED IN (streak=1)
...
[watchdog][SESSION] classifieds task 62 NOT LOGGED IN (streak=13)
```
共两波污染（Wave 1: tasks 32–39；Wave 2: tasks 49–62），共 19 个 episodes 无效。

**根本原因**：PHP 默认 `session.gc_maxlifetime=1440`（24 分钟）。Agent 运行时 PHP 服务器端 session 文件被 GC 回收：
- Playwright 持久化到 `.auth/classifieds_state.json` 的 cookie 仍有效（客户端）
- 但服务器端 session 文件已被删除（服务器端）
- 结果：cookie 发出，服务器找不到对应 session → 视为未登录状态

**两波污染成因**：
- Wave 1：容器 reset 后 auth 刷新了一次（约 17:10），但 24 分钟后再次过期
- Wave 2：watchdog 检测到 streak=8 时系统碰巧出现一个有效 session（"login restored"），但没有真正刷新 auth；24 分钟后第二波过期从 task 49 开始

**修复**：
1. **运行时修复**（当次实验）：`docker exec classifieds sh -c "echo 'session.gc_maxlifetime = 86400' > /usr/local/etc/php/conf.d/session-lifetime.ini && kill -USR2 1"` → PHP 生命周期延长到 24 小时
2. **永久修复**：在 `reset_vwa.ps1` 中追加：
   ```powershell
   if ($Site -eq "classifieds" -or $Site -eq "all") {
       Write-Host "[reset] extending classifieds PHP session lifetime to 86400s (24h)..."
       docker exec classifieds sh -c "echo 'session.gc_maxlifetime = 86400' > /usr/local/etc/php/conf.d/session-lifetime.ini && kill -USR2 1 2>/dev/null; echo done"
   }
   ```
3. **数据清理**：`clear_tasks.py --tasks 32-35,38-39,49-60,62` 删除 19 个 NOT_LOGGED_IN 的 SOM episodes。

**教训**：
- classifieds 每次 reset 后不仅需要刷新 `.auth/classifieds_state.json`（Playwright 重新登录），还需要延长 PHP session 生命周期，否则不到 30 分钟 session 再次失效
- watchdog 的 `[SESSION] login restored` 消息并不意味着 auth 被主动刷新，只是某个 task 碰巧返回了有效 session；不能依赖它自动恢复
- **正确的 classifieds reset 全流程**（依次）：
  1. PowerShell reset（docker rm + compose up）
  2. 等待 90s MySQL 初始化
  3. 执行 `init_db.sh`（Bug A 修复）
  4. 延长 PHP session 生命周期（Bug B 修复）
  5. Playwright 重新登录刷新 `.auth/classifieds_state.json`

## 40. B0 proxy_api_agent Prompt 三处缺陷 + API 503 无重试（2026-04-13） [bug]

B0 SOM condition 跑出 33 episodes 后，发现成功率仅 3%（1/33），远低于 B1 4B 模型的 20.5%。分析 runner log 和 step 数据后定位四个独立问题。

---

### 40.1 现象：速度异常快 + 成功率极低

| 指标 | 值 | 预期 |
|------|-----|------|
| 成功率 | 1/33 (3.0%) | >15%（强于 B1 4B 的 20.5%) |
| avg 步数 | 9.1 步/episode | ~15-20 步 |
| avg 耗时 | 49.5s/episode | 正常（API 延迟合理） |
| Action cycle 早停 | 29/33 episodes (88%) | 极少 |
| API 503 错误 | 10 次 | 0 |

速度快的原因：绝大多数 episode 在 3-8 步就被 action cycle 检测截断（3 次相同动作无进展），并非真正高效完成任务。

---

### 40.2 Bug 1：Scroll 方向说明缺失（最主因）

**`proxy_api_agent.py` 原 prompt（第 81 行）**：
```
3. Scroll: {"action_type": "scroll", "delta": [dx, dy], "coordinate_type": "normalized"}
```
无任何 dy 正负方向说明。

**B1 `qwen3vl_agent.py` 的对应行**：
```
3. Scroll: {"action_type": "scroll", "delta": [dx, dy], "coordinate_type": "normalized"}
   - dy>0 scrolls DOWN, dy<0 scrolls UP. Use scroll up when the target is above the current view.
```

**后果（task 21 实测）**：
```
目标：找 RVs+campers 下拉菜单
模型 thought: "I should scroll DOWN through the dropdown"
实际 action: scroll delta=[0, -0.5]   ← 负值 = 向上！
结果：连续 3 次向上滚动，page_changed=False，触发 action cycle 早停
```
235B 模型对 VWA 坐标约定没有先验知识，未加说明时猜错方向。

**修复**：在 scroll schema 下加一行说明，与 B1 一致。

---

### 40.3 Bug 2：History 把 `page_changed=False` 错标为 `FAILED`

**`proxy_api_agent.py` 原 history formatter**：
```python
if success is False or changed is False:
    result = "FAILED (page unchanged)"   # ← 两种完全不同的情况合并了
elif changed:
    result = "OK (page changed)"
else:
    result = "OK"
```

当 `action_success=True`（动作执行成功）但 `page_changed=False`（页面内容没变化）时，history 显示 **FAILED**。模型误认为自己的动作失败了，继续重试相同动作，加剧 action cycle。

**B1 的正确做法**：
```python
if success is False:
    result = "FAILED"
elif changed:
    result = "OK (page changed)"
else:
    result = "OK (page unchanged)"   # 动作成功，只是页面没变化
```

**修复**：分离 `action_success=False`（真失败）和 `page_changed=False`（无变化但动作本身成功），后者改为 `OK (page unchanged)`。

### 40.4 Bug 3：CRITICAL 节缺少「避免重复动作」提示

**B0 原 CRITICAL**：无此条。

**B1 CRITICAL 末尾**：
```

```

**后果（task 26）**：步骤 5-8 全部 scroll down，`page_changed=False`（已到底），模型 thought 几乎逐字相同——"I need to scroll down to see more..."，直到 action cycle 截断。

**修复**：在 `proxy_api_agent.py` CRITICAL 末尾加入与 B1 一致的提示。

---

### 40.5 Bug 4：API 503 无重试

`proxy_api_agent.py` 的 API 调用为：
```python
resp = requests.post(endpoint, ...)
resp.raise_for_status()   # 503 直接抛出，不重试
```

运行 33 个 episodes 期间 503 错误出现 **10 次**（~30% 时段 API 不稳定），导致这些 episode 直接失败。

**修复**：加 exponential backoff 重试（最多 3 次，等待 10s→20s→40s），可重试状态码：429/500/502/503/504。

```python
_retryable_codes = {429, 500, 502, 503, 504}
for _attempt in range(4):
    resp = requests.post(...)
    if resp.status_code not in _retryable_codes or _attempt == 3:
        break
    wait = 10 * (2 ** _attempt)
    logger.warning("API %s, retrying in %ds...", resp.status_code, wait)
    time.sleep(wait)
resp.raise_for_status()
```

## 41. Gallery 幽灵 Episode 根因 + 孤儿文件双重清理（2026-04-13） [bug][infra]

清除 B0 SOM 33 个脏 episodes 并重启 B0 后，gallery 仍然显示旧 SOM 数据（task_63 等）。排查后发现问题根因比预想的更深，涉及两类孤儿文件。

---

### 41.1 问题：清空 episodes 目录后 gallery 仍显示旧数据

**现象**：
- `clear_tasks.py` 已清除 33 个 SOM episodes（summary + steps + artifacts）
- `phase1_som_router_0/episodes/` 目录为空
- `generate_gallery.py` 报告 "10 episodes" 但其中包含 SOM task_63

**根因 1：Gallery 以 steps JSONL 为主索引，而非 summary**

`generate_gallery.py` 的核心循环（约第 332 行）：
```python

```
即：gallery 扫描 **steps 文件**，summary 是可选加载项。只要 steps 文件存在，就会产生一张 episode 卡片。

**根因 2：旧版 watchdog auto-retry 只删 summary，遗留 steps 文件**

task_63 的历史路径：
1. 早期运行中出错，watchdog auto-retry 触发
2. 旧版 watchdog（§39 前）的 auto-retry 代码只删了 `*_summary_v2.json`，而 **遗漏了 `*_steps_v2.jsonl`**
3. 手动 `clear_tasks.py` 时，只列出了有 summary 的 tasks → task_63 不在列表内 → steps 文件残留

**根因 3：artifact 目录同理**

task_25、task_29、task_63 的 artifact 目录也被旧版 watchdog 遗留（同样只删了 summary）。Gallery 渲染截图时读取 artifacts，孤儿 artifact 目录也导致幽灵 episode。

### 41.2 完整根因链

```
旧版 watchdog auto-retry（§39 前）
  ├── 删 *_summary_v2.json   ✓
  ├── 删 *_steps_v2.jsonl    ✗ 遗漏
  └── 删 artifacts/          ✗ 遗漏
         ↓
孤儿 steps 文件    → gallery 主循环读到 → 幽灵 episode 卡片
孤儿 artifact 目录 → gallery 截图渲染  → 显示旧截图
         ↓
clear_tasks.py 只处理有 summary 的 tasks
→ 孤儿 steps/artifacts 不在清理范围
→ gallery 重生成后幽灵数据依然存在
```

> 注：§39/§40 中修复后的 watchdog auto-retry 和 session_contaminated 清理路径均已正确删除 summary + steps + artifacts，此问题仅影响修复前产生的历史孤儿数据。

### Fix 3 — vwa_wrapper：type+element_id 路径补发 Enter

**文件**：`p79/envs/vwa_wrapper.py`

**根因**：VWA `create_id_based_action(f"type [{eid}] [{text}]")` 的 id-based parser 在 `_json_to_id_action_str()` 中对 text 做 `replace("\n", " ")`，导致搜索表单的 `\n` 结尾被 strip，提交动作丢失。

**修复**：在 `type + element_id` 且 `element_id > 0` 的分支，记录 `_type_needs_enter` 标志。`self._env.step(action)` 之后，若该标志为 True，补发 `keyboard.press("Enter")` + `wait_for_timeout` + `create_none_action()` 刷新观测。

```python
# 位置 A：step() 开头
_type_needs_enter = False

# 位置 B：type+element_id 有效分支
else:
    _type_needs_enter = bool(str(action_json.get("text", "")).endswith("\n"))

# 位置 C：self._env.step(action) 之后
if _type_needs_enter and self._env is not None:
    try:
        self._env.page.keyboard.press("Enter")
        self._env.page.wait_for_timeout(int(self.sleep_after_execution * 1000))
        re_obs, _, _, _, re_info = self._env.step(create_none_action())
        obs, info = re_obs, re_info
    except Exception as _e:
        logger.warning("Post-type Enter press failed: %s", _e)
```

**影响范围**：DOM + SoM 两种模式下所有搜索/表单提交（`text.endswith("\n")`）；Vision 模式使用 `keyboard_type_action`（含 `\n`），不受影响。
