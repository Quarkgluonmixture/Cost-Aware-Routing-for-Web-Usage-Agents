## 3. Phantom-SoM: Definition and Ablation Setup

### 3.1 Set-of-Mark Bundle

Set-of-Mark (SoM) prompting converts a screenshot into an indexed visual interface. The standard bundle has two synchronized parts: a marked image, where page regions are overlaid with bounding boxes and numeric IDs, and a text legend that maps those IDs to element descriptions [Yang et al. 2023]. We serialize the text component as:

```text
[SOM_MARKS]
[id=N] role 'label'
...
[/SOM_MARKS]
```

Full SoM gives both pieces to the agent at the same step. The prompt says the `[SOM_MARKS]` list and annotated screenshot refer to one another, and the action schema asks the model to click, type, or select by `element_id` when possible. VisualWebArena and SeeAct use the same broad pattern: visual evidence is paired with grounding information so the model can convert perception into browser actions [Koh et al. 2024; Zheng et al. 2024].

This bundle is the assumption Phantom-SoM ablates. The question is not whether marked screenshots are useful; Section 4 shows that they often are. The question is whether the text half of the bundle is only an image key, or itself a distinct text representation.

### 3.2 Phantom-SoM

We define **Phantom-SoM** as:

```text
Phantom-SoM(page) =
  prompt = SoM prompt
  text   = SOM_MARKS(page)
  image  = None
```

Phantom-SoM uses the same SoM prompt family as full SoM and the same `[SOM_MARKS]` text, but removes the page screenshot passed to the model. In code, `p79/experiment/som.py::prepare_observation_for_mode` handles `mode in ("phantom_som", "phantom_dom", "phantom_text")` by calling `_build_som_result(...)`, then returning the generated `som_text` with `marked_image=None` (`phantom_dom` is the **deprecated legacy mode value** — A1.7 B-261 enforces fail-loud `ValueError` raise in `conditions.py:96-117` when encountered in any new yaml to prevent `resume:true`-driven silent overwrite of `phantom_text` data; pre-A1.7 archive run dirs `phase1_phantom_dom_router_0/` remain readable via `run_registry.py` backward-compat normalization `phantom_dom + phantom_text → "P-text"`; `phantom_text` is the current canonical name). The rendered screenshot path is retained for debugging; the model does not receive it.

The critical property is that the prompt remains the SoM prompt. It still describes an annotated screenshot with numbered boxes, even though the observation channel contains no page screenshot. We call this the **mirage prompt** property: the behavioral scaffold of SoM is preserved while the visual substrate is removed.

Phantom-SoM is a cost intervention, and the structure of the saving is best stated relative to two different baselines.

**Relative to DOM**, Phantom-SoM is essentially free. The `[SOM_MARKS]` block is produced by a regex filter over the VisualWebArena accessibility-tree text that the DOM baseline already consumes. VWA serializes interactive elements with bracketed numeric IDs of the form `[N] role 'label'`; in our implementation `_extract_text_marks` (see `p79/experiment/som.py`) walks `obs_text` line by line, keeps the lines that match `\[\d+\]`, and returns `(id, label)` pairs that are wrapped in a `[SOM_MARKS] ... [/SOM_MARKS]` block. There is no bounding-box lookup and no image work in this path; bounding boxes are only used by full SoM when drawing numeric labels onto the screenshot. Empirically this leaves text length roughly unchanged: holding the system prompt fixed at the DOM family, median total input is 3437 tokens for DOM versus 3661 for P-text on reddit, and 3008 versus 2948 on classifieds — within ±7% on both sites. The two formats see the same accessibility content; what differs is the surface form (flat indexed list versus nested hierarchy with url/tab metadata). We treat this as a representation property and study its behavioral effect mechanistically in Section 5; for cost accounting the implication is that switching DOM → Phantom-SoM at deployment time costs at most a regex pass over the same observation.

**Relative to full SoM**, Phantom-SoM saves two real layers of cost. (i) The on-server annotation step that draws numeric labels onto the page screenshot is unique to full SoM and is omitted in a Phantom-SoM deployment; in our research code we retain the marked image on disk for debugging, which is why both modes report ~30 ms median obs-prepare latency, but a production variant skips the draw entirely and recovers roughly 30 ms and on the order of $2e-5 per step. (ii) The marked screenshot is no longer encoded as image tokens at inference, removing the visual-encoding stage. Comparing step-level `tokens.input` medians between full SoM and P-text gives a same-prompt image-channel estimate of 733 input tokens per step on reddit (SoM 4275 versus P-text 3542; P-text partial live run, 145 episodes) and 1064 on classifieds (4034.5 versus 2970.5; 234 episodes). We attribute this median gap to the marked screenshot under our backend tokenization. These are the tokens that drive prompt-processing time, memory pressure, and time-to-first-token in multimodal serving (see Section 2.4); skipping them is the dominant component of the cost difference between full SoM and Phantom-SoM.

The combined picture is that Phantom-SoM sits at roughly DOM cost (its observation is a text filter of the same AXTree) while replacing the visual-evidence half of SoM with nothing at all. This is also a deployment-level claim, not only an analytical one: an existing full-SoM agent can be converted into a Phantom-SoM agent by changing only what the server forwards to the model — keep the `[SOM_MARKS]` text that is already being produced from the accessibility tree, stop drawing labels onto the screenshot, and stop attaching the marked image to the inference request. The model interface, the prompt, the action schema, and the evaluator are unchanged. There is no retraining, no new data path, and no marks-side prompt edit; the only mutation is on the backend annotation pipeline, after the AXTree filter and before the model call. We use this property in Section 4 to interpret cost-versus-success comparisons as deployment-time tradeoffs rather than research-only configurations, and in Section 5 to argue that Phantom-SoM's behavior is a property of the format the model already saw inside SoM, not an emergent capability that requires new infrastructure.

### 3.3 P-text

**P-text** is the disambiguation ablation:

```text
P-text(page) =
  prompt = DOM prompt
  text   = SOM_MARKS(page)
  image  = None
```

Its observation is identical to Phantom-SoM: `[SOM_MARKS]` text only, no page screenshot. The only intended change is the system prompt. In both B0 (`p79/agents/proxy_api_agent.py`) and B1 (`p79/agents/qwen3vl_agent.py`), `_system_prompts["phantom_som"]` maps to the SoM prompt, while `_system_prompts["phantom_dom"]` (and the alias `_system_prompts["phantom_text"]`) maps to the DOM prompt. For `som`, `phantom_som`, `phantom_dom`, and `phantom_text`, the agent passes through the `[SOM_MARKS]...[/SOM_MARKS]` text directly.

This cell separates representation from prompt wording. If P-text behaves like Phantom-SoM, the flat marks text is driving behavior. If it behaves like DOM, the prompt is doing more of the work.

### 3.4 The Complete 2×2 Ablation Matrix and the P-prompt Fourth Cell

The core ablation is a complete prompt-by-representation matrix:

| | DOM prompt | SoM prompt |
|---|---|---|
| AXTree obs | DOM | **P-prompt** |
| `[SOM_MARKS]` obs | P-text | Phantom-SoM |

Full SoM is adjacent to this 2×2: it uses the SoM prompt, the same `[SOM_MARKS]` text, and the marked screenshot. Vision is a separate screenshot-only baseline. Together with the 2×2 above, this yields the six modes we evaluate empirically: DOM, P-text, P-prompt, Phantom-SoM, full SoM, and Vision.

### 3.4.1 P-prompt (AXTree observation + SoM prompt)

**P-prompt** is the fourth cell of the 2×2:

```text
P-prompt(page) =
  prompt = SoM prompt
  text   = AXTree(page)
  image  = None
```

The agent receives the AXTree accessibility-tree text the DOM baseline already consumes, but under the SoM system prompt — i.e. the model is told to act on an annotated screenshot with numeric IDs even though no such image is present and the text is hierarchical AXTree, not the flat `[SOM_MARKS]` form. In code, `_system_prompts["phantom_prompt"]` maps to the SoM prompt family and the observation channel passes through the unmodified AXTree text (no `[SOM_MARKS]` filter applied).

This cell is intentionally a mismatched-format-against-prompt design point. The SoM system prompt expects a **flat compressed listing** of `[N]` references (the `[SOM_MARKS]` block produced by `_extract_text_marks` regex-filtering the AXTree), while the AXTree text **embeds the same `[N]` IDs inside a nested hierarchical structure** with role labels, parent-child indentation, and url/tab metadata. The two surface formats expose the same underlying AXTree IDs in incompatible structural contexts; the mismatch is one of representation format, not of identifier values (prose corrected post /stress A1.10 P0-8-C* "ID space disagreement" hallucination catch 2026-05-16 — SOM_MARKS literally shares AXTree IDs per `som.py:46-50`). There are three substantive reasons we include P-prompt rather than excluding it as a malformed hybrid:

(i) **The 2×2 isolates the prompt-format axis independently of the text-representation axis.** Without P-prompt, the prompt wording effect can only be measured along `[SOM_MARKS]` text (P-text vs Phantom-SoM). P-prompt gives the corresponding contrast on AXTree text (DOM vs P-prompt), so the 2×2 is identified at both rows rather than only at one.

(ii) **The prompt-text ID-space disagreement is the manipulated variable, not a confound.** The 2×2 manipulates two binary factors (prompt family ∈ {DOM, SoM} × text format ∈ {AXTree, `[SOM_MARKS]`}); the off-diagonal cells (P-text, P-prompt) by construction expose the model to combinations its training distribution would consider mismatched. P-prompt's "SoM prompt over AXTree text" is therefore the design point that probes whether the SoM prompt's behavioral effect generalizes off-distribution — not an accident to be apologized for. Whether the model collapses on this cell or adapts is the experimental outcome; either result identifies the prompt-format effect along the AXTree row of the 2×2.

(iii) **P-prompt anchors the H3 axis-2 structural claim.** The pre-registered H3(ii) hypothesis (`preregistration.md` §2) tests whether |P-prompt ∖ P-SoM| unique-task contribution is non-zero — i.e., whether the SoM-style prompt elicits behavior P-SoM does not when paired with hierarchical text. Without P-prompt cell data, H3 axis-2 cannot be tested, and the paper's structural claim collapses to a single-axis (R2) framing.

**Disclosure (added in response to cross-AI methodology audit, 2026-05-15).** A natural objection is that P-prompt's `[N]` ID references in the SoM prompt cannot in general match the AXTree's hierarchical ID space, so any failure should be attributed to prompt-text incoherence rather than to the prompt-family axis. We agree with the mechanism and disagree with the framing: that incoherence is the variable we are manipulating. We therefore (a) treat P-prompt's action-parse-success rate as a first-class reported metric alongside SR, not a confound to be regressed out (Section 4 transparency); (b) do not interpret P-prompt SR collapse as evidence against H3 — collapse and partial-success are both informative outcomes; (c) anchor the structural claim on the unique-task contribution |P-prompt ∖ P-SoM| rather than on raw P-prompt SR, so the claim is robust to either outcome.

### 3.4.2 Contrast Logic

Each contrast isolates a different factor:

- **DOM vs P-text** holds the prompt family fixed at DOM and changes the text-payload structure from AXTree to `[SOM_MARKS]`.
- **DOM vs P-prompt** holds the text observation fixed at AXTree and changes only the prompt family.
- **P-text vs Phantom-SoM** holds the text observation fixed at `[SOM_MARKS]` and changes only the prompt family. Together with DOM vs P-prompt, this gives two independent measurements of the prompt-format axis.
- **DOM vs Phantom-SoM** changes both axes — text-payload structure AND prompt — measuring the combined within-phantom diagonal.
- **Full SoM vs Phantom-SoM** holds prompt and marks text fixed and adds the implemented marked-image channel.
- **Full SoM vs DOM** measures the combined effect of SoM prompt, marks text, and marked screenshot relative to the standard text baseline.

The 2×2 is not a routing policy by itself. It is a causal scaffold for Section 5: text-payload structure shapes exploration, while prompt wording tunes commitment confidence. Section 6 maps this scaffold onto **two complementary router operating points** (not a single 4-step cascade — prose corrected post /stress A1.10 P1-8-C* token-monotonic-cascade-vs-latch catch 2026-05-16): the v3/v4/v5 **rule-based escalation router** moves one mode at a time per trigger along the user-specified `modes` list (`router.py::RuleBasedRouter.decide` lines 142-156, `decision = self.modes[min(current_idx + 1, len(self.modes) - 1)]`); the v6 **pareto-cascade variant** instead jumps directly to a configured `safe_fallback_target` (default Phantom-SoM) and latches there for the remainder of the episode (`router.py::RuleBasedRouter.decide` lines 130-141, `state.fallback_latched = True`). Paper-1 reports the single-step rule-based variant; the v6 jump-and-latch cascade is deferred to a follow-up paper. P-prompt sits off both router paths as the diagonal cell that completes the prompt-format identification.

### 3.5 Implementation and Measurement Protocol

All SoM-derived conditions share the same text-marks extractor. `_extract_text_marks` reads `obs_text` (the VisualWebArena accessibility-tree serialization the DOM baseline already uses) line by line and keeps each line whose first non-whitespace token is the bracketed numeric id followed by a role label — the canonical anchored regex `^\s*\[(\d+)\]\s+\w` defined as `MARK_ID_DETECT_RE` in `p79/experiment/som.py` (post-/stress A1.10 P1-2 sibling propagation). Bracketed digits embedded inside StaticText content (e.g. `"see [4] above"`) are therefore excluded by construction. The extractor produces `(id, label)` pairs up to a configured cap. `_build_som_result` then wraps those pairs in a `[SOM_MARKS] ... [/SOM_MARKS]` block. This text path **does not require bounding boxes**: the IDs come from the accessibility tree, not from a separate vision pipeline. Bounding boxes are only consulted by full SoM, which uses `obs_nodes_info` to draw numeric labels onto the page screenshot. Phantom-SoM and P-text reuse the exact `[SOM_MARKS]` text and drop the page screenshot; Marks are not re-filtered specifically for Phantom, and the source page state is unchanged.

Reference images supplied by a task configuration are separate from the observation mode. These task-provided target images are passed to all modes as task input; Phantom-SoM removes only the current-page browser screenshot.

**SoM mode degradation rate (empirical).** Full SoM has two designed fallback paths inside `_build_som_result` (`p79/experiment/som.py`): a *zero-marks* path where the `[SOM_MARKS]` extractor returns no IDs and the agent falls back to the raw (unmarked) page screenshot under the SoM prompt; and an *image-render* path where `[SOM_MARKS]` text is built successfully but the PIL bounding-box draw on the screenshot raises an exception and the marked image is dropped, leaving the agent with `[SOM_MARKS]` text under the SoM prompt and no image at all. Post-/stress A1.4 P0-2 (2026-05-17) the schema field `step_record.som.degraded_som` is **removed** — it was a single bool overloading three semantically distinct states (zero-marks vision-fallback, render-fail phantom-fallback, phantom-mode inherit where "no image" is design intent) and empirically fired `0/6 471` (0.00 %) of Phase 1 SoM-mode step records. Path A (zero-marks) is now detected aggregator-side via `step_record.som.mark_count == 0`; Path B (PIL render-fail) is signaled only via `logger.warning` in `_build_som_result` (no schema field). We checked this empirically on the completed Phase 1 B0 + B1 SoM archive (B0 reddit + B1 classifieds + B1 reddit, 6 471 SoM-mode step records total): no step has `mark_count == 0` (minimum observed is 1, typical full-page bucket 21–100 marks); the WARN log shows zero render-fail events. Both fallback paths are therefore latent on Phase 1 archive data and the published SoM SR is the true 3-piece-bundle outcome. We re-verify the same rate on Phase 1a clean-rerun data after fire because B2 (Gemma3-VL, added 2026-05-14) has no archive coverage; if B2 SoM `mark_count == 0` rate exceeds 5 % on any Phase 1a cell, we annotate the Section 4 SR table with the rate and split the SoM rollup into "3-piece SoM" versus "marks-empty fallback" before re-running the paper-grade aggregator.

Each episode starts from `environment.reset(task.config_file)`, and paper-grade condition comparisons use freshly reset site state to avoid cross-condition contamination. The April 27 Magento base-url/auth fix addressed an unrelated shopping-state reliability issue; this paper uses completed classifieds and reddit runs under the reset protocol.

All reported confidence intervals use task-level paired bootstrap resampling with B=1000 draws and analysis RNG `seed=42`, pinned in `p79.experiment.analysis._compute_statistical_tests` and reused by `scripts/analysis/aggregate_phantom_lift.py` + `aggregate_phase1_prereg_gate.py`. The H1 PRIMARY gate (FE inverse-variance pool of P-SoM drop-one over six planned (site, model) cells) uses the same seed via `scripts/analysis/aggregate_phase1_prereg_gate.py`.

**Statistical testing infrastructure.** Across the analysis pipeline three independent paired tests are reported alongside the bootstrap CI: a McNemar exact test paired by `task_id` (`analysis.py::_mcnemar_per_pair`, merge-key correctness verified after the audited 2026-05-16 fix to the per-task merge that previously matched on episode order rather than `task_id`), a Wilcoxon signed-rank test on per-task SR differences with the standard zero-difference exclusion, and a TOST equivalence test at δ = 1.0pp (`analysis.py::_tost_pair`). When a Wilcoxon comparison is *skipped* — because the per-task paired-difference vector is degenerate (all zeros, all ties, or N < 6) — the skip event is logged into `analysis/wilcoxon_skipped.csv` with the skip reason rather than being silently absorbed into the test family. Multiplicity control is Holm-Bonferroni step-down, applied **per (test, metric) sub-family** independently rather than across the union of all tests — this matches the pre-registered family-declaration in `preregistration.md` §3 and avoids over-correcting tests that probe distinct estimands (`analysis.py::_holm_correct`). The Pareto frontier in `_compute_pareto_front` uses strict-`<` dominance: an arm is on the frontier only if no other arm is **strictly** better on every dimension. Arms that tie on every dimension with a frontier point are kept on the frontier rather than collapsed, which is the conservative tie semantics for cost-success scatter visualizations.

**Schema integrity guarantees.** Episode summaries and step records use schema version 2.0, defined by `EpisodeSummaryV2` / `StepRecordV2` dataclasses in `p79/experiment/types.py` and validated at write time by `validate_step_record_v2` (which derives its required-field set from `dataclasses.fields(StepRecordV2)` at import time, type-checks each field's container shape, and requires paper-grade critical optional keys — `parse_valid`, `parse_failure_reason`, `image_meta`, `locator_route_meta`, `agent_visible_changed` — to be present even when their value is `None`, so the difference between "no image observed" and "field omitted by an older runner" is recoverable from the JSONL alone). Episode and run summaries have parallel `validate_episode_summary_v2` and `validate_run_summary_v2` validators that enforce the same dataclass-derived contract plus explicit type checks on the paper-1 hero fields (`success` must be bool, `score` numeric, `task_id` int). The runner writes JSONL step records and JSON episode summaries through `LoggerV2` (`p79/experiment/logger_v2.py`), which performs an atomic `os.replace(tmp, target)` followed by an `fsync` on the containing directory — so a host-side crash between the rename and the journal flush cannot leave the analysis pipeline reading a half-written summary. Per-step JSONL writes also flush and `fsync` the open file descriptor before returning, and `LoggerV2.__init__` `fsync`s the condition directory after creating `episodes/`, so the episode subtree is committed to stable storage before the first step record lands. Per-step `fsync` is intentional: on the A100 self-host fire each call is roughly 10 ms on the local SSD, so the 42-condition Phase 1a accumulates on the order of 14 minutes of disk-flush time across all step records. We do not subtract this from `latency_ms.total`, because the three baselines write identical schemas and therefore incur the same durability overhead per step — the B0/B1/B2 (and within-cell phantom) comparison stays apples-to-apples even though absolute latency includes the cost of being crash-recoverable. On the read side, `read_jsonl_dedup` (`p79/experiment/io_utils.py`) handles restart deduplication (with a step_idx-decrement fallback when a JSONL has no `step_idx == 0` line, so a crash that loses the first step record cannot silently mix earlier-run and later-run records into a single segment), counts corrupt lines, opens files with `errors="replace"` so a stray non-UTF-8 byte does not terminate analysis, and emits an `analysis/jsonl_integrity_report.csv` listing per-file `corrupt_lines`, `dedup_discarded`, `summary_identity_mismatch` (which is `None` when no summary was supplied for the identity check rather than the misleading `False`), and `step_idx_non_monotonic` flags. Outcome aggregators consume episode summaries through `load_episode_summary_strict` (`p79/experiment/io_utils.py`), which refuses inputs where `success` is anything other than a Python bool — preventing the string-truthy contamination where a JSON literal `"success": "false"` would otherwise read as truthy under Python `bool(...)` and inflate the reported success rate. Optional step-record fields (`parse_valid`, `parse_failure_reason`, `fallback_finish`, `image_meta`, `image_meta_recorded`, `locator_route_meta`, the 5 retry/GLM-rescue de-biasing fields, plus the canonical episode-summary fields in `EPISODE_SUMMARY_V2_DEFAULTS`) are normalized through the `fill_step_defaults` / `migrate` helpers in `p79/experiment/schema_migrations/v2.py` before `_collect_episode_summaries` aggregates them, so an aggregator never observes a field as silently `KeyError`-absent versus deliberately `None` — the source of truth for "what fields exist at v2" is the dataclass catalog plus its defaults, not the runner's emission order. Corrupt rows, dedup discards, and identity mismatches surface in `jsonl_integrity_report.csv` rather than being silently dropped, so contamination cannot reach a paper-grade figure without first appearing in a transparency artifact.

When comparing arms, we use same-task subsets: a task contributes only when the relevant conditions have completed it. The reported outcome is the canonical **success** field on each episode summary, with no post-hoc adjustment. Two upstream interventions ensure this raw number is the paper-grade outcome rather than a contamination of false positives: (i) tasks with `eval.fuzzy_match == "N/A"` are excluded at the task-load layer (`tasks.py::_is_na_task`, default `task.exclude_na_tasks: true`), so not-applicable tasks never enter the comparison universe; (ii) the VisualWebArena LLM-judge helper functions (`llm_fuzzy_match` and `llm_ua_match`) are patched at the evaluator level to return `0.0` deterministically when the predicted answer is empty or whitespace-only (VWA submodule branch `p79-patches` commit `f0c835b`), which closes the failure mode where the runner's fake-stop with `answer=""` was being credited as a correct answer by the LLM judge. The combined effect is that `success` is now the canonical outcome with no per-condition false-positive subtraction layer; the historical `compute_adjusted_success` post-hoc layer and its `na_fp`/`eval_fp`/`adjusted_success` derived fields have been retired (see `analysis.py` and `EpisodeSummaryV2`). Section 4 reports results under these conventions; Section 5 uses the same traces for mechanism analysis.

**LLM-judge model disclosure.** The LLM judge invoked by `llm_fuzzy_match` / `llm_ua_match` is configurable via the `VWA_EVAL_MODEL` / `OPENAI_EVAL_MODEL` environment variables, with default `gpt-4o-mini` (VWA submodule branch `p79-patches` commit `3f9ceca`). Upstream VisualWebArena hard-codes `gpt-4-1106-preview` (a GPT-4-turbo preview model). Cross-paper SR comparisons against the original VWA paper, WebArena-Verified, or PAE — all of which scored string-match tasks with `gpt-4-1106-preview` — are therefore not directly comparable: any per-task disagreement between the two judges is folded into the cross-paper baseline delta. We adopt `gpt-4o-mini` for cost (≈ 10× cheaper per judge call than `gpt-4-turbo`) and because the upstream `gpt-4-1106-preview` model is a deprecated preview alias on the OpenAI API; the empty-prediction guard from (ii) above closes the dominant FP source under either judge model, but does not bridge the capability drift between judges on non-empty borderline predictions. We do not claim `success` numbers from §4 are directly comparable to prior-paper numbers without re-running the prior baselines under the same `VWA_EVAL_MODEL`; internal P79 paired comparisons (DOM ↔ P-SoM, baseline ↔ phantom within the same cell) remain valid because every cell is judged by the same `gpt-4o-mini` default.

**Type-action clear-before-type behaviour.** Upstream VWA's `execute_type` action appends to whatever text already occupies the target input field; when an agent retries a `type` action against a field that the previous attempt partially populated, the new text concatenates onto the residual text and the resulting field value is rejected by the evaluator even though the agent intended to overwrite. P79 mitigates this at two layers. (1) **Submodule layer** (VWA `actions.py` commit `3f9ceca`): the `execute_type` / `aexecute_type` dispatch is extended so that every type path — id-based, role+name-based, and Playwright-locator-based, sync and async — prepends `Meta+A` + `Backspace` before the keystroke stream. This is a defensive fallback for any runner that invokes VWA's action layer directly. (2) **Wrapper layer** (`p79/envs/vwa_wrapper.py`, Cluster 1 fix on 2026-04-19): the P79 runner overrides the dispatch with `locator.fill(text)`, which is atomic over (clear, type) and avoids the `Meta+A` side-effect where, if the prior click misses the input element, the page-level `Meta+A` selects all visible text instead of the field — manifested historically as the "全选变蓝" symptom (实验笔记 §52, B-01 in `master_bug_catalog.md`). Paper-grade Phase 1a uses the wrapper-layer override end-to-end, so the headline numbers are not affected by the submodule-layer `Meta+A` fallback; the fallback is retained for upstream-compatibility with raw-VWA reproducers and is disclosed here for cross-paper reproducibility scope.

### 3.5.1 Cross-baseline implementation asymmetries (disclosure)

Three baseline-level implementation differences are not eliminated by the design above and we disclose them here rather than treat them as bugs.

**Effective scroll action vocabulary.** Although all three baselines see the eight-action schema described above, the *effective* scroll action space differs between B0 (proxy) and B1/B2 (local). B0's system prompt emits `scroll_direction ∈ {"up", "down"}`, and the agent post-processes the response into a fixed magnitude `delta = [0, ±0.8]` (`proxy_api_agent.py::step`, the `scroll_direction → delta` translation block). B1 and B2 instead receive a `delta = [dx, dy]` schema and the model selects the magnitude per step. Cross-baseline SR differences on scroll-heavy tasks (notably reddit search-loop episodes) therefore mix a capability gap with an action-vocabulary asymmetry; we do not claim byte-equivalence at the action-space level and Section 4 does not interpret scroll-driven SR deltas as pure capability effects.

**Per-mode input-token decomposition.** B1 and B2 record `input_image_tokens` and `input_text_tokens` separately from the local processor (`qwen3vl_agent.py:521`, `gemma3vl_agent.py:226-229`), so the cost saved by removing the page screenshot from a marks-only mode is directly measurable. The B0 proxy returns only an aggregate `usage.input_tokens` (no per-modality decomposition; `proxy_api_agent.py::meta`), and the runner therefore writes `input_image_tokens = 0` for B0 in every step record. Absolute B0 cost numbers per mode are not comparable to B1/B2 absolute numbers at the per-image-token granularity. The "Phantom-SoM cost ≈ DOM" property is therefore measured *within* each baseline as the cross-mode delta `Δusage(mode_with_image) − Δusage(mode_without_image)` rather than as an absolute per-image cost across baselines.

**Action-success attribution semantics under optional retry.** When M3 fallback retry (`module_flags.m3_failure_trigger_retry`, paper-2 ablation Phase 3) or the runtime-level `baseline_retry_on_no_progress` knob is enabled, a step that initially fails its primary action may execute a single corrective retry action (scroll / click / wait, per `p79/experiment/modules.py::m3_retry_action`); the recorded `step_record.action_success` then reflects the **final outcome of the (action ∨ retry) chain**, not the primary action in isolation. To disambiguate, `step_record.retry_action_applied` (bool) and `step_record.retry_action_type` (str) are emitted, and any per-action-type aggregation in `scripts/analysis/` that wants to attribute success only to the primary action MUST filter on `retry_action_applied == False`. **For paper-1 Phase 1a both flags are off by default** (`runtime.baseline_retry_on_no_progress: false` at `p79/experiment/config.py:213`, M3 module flag off in Phase 1 condition generation), so `retry_action_applied` is uniformly false on Phase 1a JSONL and the attribution issue is latent for the headline results; it becomes operative only in paper-2 Phase 3 M3 ablations where the flag is explicitly toggled. The schema fix (a dedicated `executed_action_chain` list field replacing the flat `retry_action_*` flags) is queued as a paper-2 prerequisite rather than a paper-1 remediation.

**Parse-error recovery scaffold (provisional).** B0 currently routes parse failures through an auxiliary GLM-5.1 extraction call (`proxy_api_agent.py::_call_glm_extract`, enabled by `use_glm_fallback: true` in B0 configs), which converts a malformed B0 response into a valid action. The architectural cause is that the proxy API does not forward `tool_choice` to the underlying Bedrock model, so B0 cannot be forced into structured JSON output. B1 and B2 (local Hugging Face models) have no such fallback path. We record `glm_fallback_used` and `glm_original_fail_reason` on every step so the rescue rate is auditable, and we are evaluating whether to retire the GLM rescue and report B0 with pure parse failures instead. *(Specific paper text for this paragraph pending advisor decision; the rescue rate measured on the current B0 archive is ≈ 1.49 % of steps. Final wording will reflect whichever option lands: switching to a clean structured API path, or keeping the GLM rescue with disclosure and downstream filter.)*

**Energy / CO2 platform asymmetry (B-334 disclosure).** Per-step energy is measured via NVML on the GPU plus Linux RAPL on the CPU package (`energy_tracker.py::LightweightEnergyTracker._sampling_loop`). RAPL is an Intel/AMD-only `/sys/class/powercap/intel-rapl/` interface; on aarch64 hosts (e.g. NVIDIA Grace ARM CPU) the path does not exist and CPU power is silently `None` → the sampled total reduces to GPU-only. Phase 1a paper-grade fire runs on an A100-PCIe-40GB VM with an x86 host CPU (RAPL fires), so the published kWh and CO2 numbers in Section 4 include both GPU and CPU package power. Development sampling that previously ran on DGX Spark (Grace ARM) is therefore not directly comparable to the A100 numbers at the absolute-energy level — chronicle entries that reference DGX Spark energy figures are labelled DGX-dev and not entered into the paper §4 totals. Within-fire comparisons (B0 vs B1 vs B2, or across modes within a single baseline) all run on the same A100 host and are therefore apples-to-apples.

**Energy sampling window (B-321 disclosure).** Per-step energy aggregates GPU+CPU power samples collected by a background thread at `sample_interval_s = 0.5 s`. Prior to B-321 (A1.9), the per-step window was `[now − duration − 1 s, now]`, which on a fast step (e.g. 200 ms B0 latency) included mostly pre-step idle samples → reported step power was averaged with idle and biased toward the 50 W A100 idle TDP rather than the 300 W inference burst. The current pipeline passes a monotonic step boundary to `EnergyTracker.estimate_step` and bounds the average to `[step_start, step_start + duration]` only, and emits a per-step `energy_window_partial` flag when fewer than 2 samples fall in that window. Step-level kWh attribution is apples-to-apples across modes within a baseline, but absolute per-step energy below roughly one sample interval (≈ 500 ms) remains coarse-grained — paper §4 reports kWh and CO2 at episode and condition granularity rather than per-step.

**HARDWARE_PROFILES yaml↔dict alignment (B-320 disclosure).** When NVML measurement is unavailable for a given step (e.g. before the sampling thread has accumulated samples or on non-NVIDIA hosts), the tracker falls back to a TDP profile keyed by `hardware_profile` in the yaml config. The fallback only knows keys registered in `energy_tracker.py::HARDWARE_PROFILES`; Phase 1a fire uses the canonical `"a100_pcie_40gb"` entry (50 W idle, 300 W load) added in B-320 specifically so the yaml key matches a dict entry. A misspelled yaml key on the fallback path would now raise at `EnergyTracker.__init__` rather than silently fall back to the m2 laptop profile (5 W idle, 22 W load), which prior to B-320 would have under-quoted A100 paper-grade fire fallback energy by roughly 14×.

**Rule-based router numeric thresholds — empirically dead under cleaned-AXTree regime (A1.10 P0-1-ABC* disclosure).** `RuleBasedRouter.decide` (`router.py:32-44`) defines three numeric escalation triggers: `dom_size_threshold = 12000`, `dom_complexity_trigger = 500` (where "dom_complexity" is `text.count("\n") + 1` — the AXTree text line count, not raw DOM element count; see B-323 naming disclosure below), and `text_length_trigger = 12000`. These thresholds were calibrated pre-§4.X.5 viewport-fix on pre-cleaning full-DOM intuition. On a 5001-step Phase 1a B1 classifieds spot-check (`results/visualwebarena/phase1/B1_3mode_classifieds_20260413/`) the empirical `state_digest.text_length` distribution has p50 = 3113, p95 = 4675, max = 46591 → `pct > 12000 = 0.14 %`; `state_digest.dom_complexity` p95 = 73, max = 81 → `pct > 500 = 0.00 %`. Effective routing escalation under paper-1 cleaned-AXTree regime therefore comes 100 % from the streak counters (`unchanged_streak`, `no_progress_streak`) plus the single-step `action_failed` flag, **not** from the three numeric size triggers. We retain the trigger constants for paper-2 router recalibration substrate (which may target a non-cleaned obs path) and disclose here rather than recalibrate-and-refire because the 19 P0+P1 batch fix that landed alongside this disclosure (A1.10) does not change the streak-driven decision logic. Reviewers running `grep '"dom_size_exceeds_threshold"' phase1_*/episodes/*.jsonl | wc -l` should therefore see counts consistent with the disclosed <0.5 % fire rate, not the threshold-driven escalation behavior the inherited Python constants might suggest in isolation.

**dom_complexity field name disclosure (A1.10 P1-3 cosmetic-only correction).** The `state_digest.dom_complexity` field name in step JSONL records is **AXTree text line count**, computed as `text.count("\n") + 1` in `state_change.py:77`. It is not the raw DOM element count (which `_extract_interactive_count` separately measures via the anchored `\[(\d+)\]` regex sweep landed in A1.10 P1-2 — see same JSONL field `interactive_elements_count`). The misnomer is preserved in schema v2 for backward compatibility with archive run dirs; future schema v3 (paper-2 prep) will rename to `axtree_line_count`.

**Retry vs primary action attribution — step record schema mix disclosure (A1.10 P0-5-B* clarification).** Beyond the existing `retry_action_applied` / `retry_action_type` flags described above, paper-2 M3 ablation readers should additionally note that under retry firing the step record `action_type` / `action` payload fields still carry the **original failed action identifier**, while `action_success` / `page_changed` / `page_change_reasons` reflect the **retry outcome**. A single step JSONL row therefore mixes action-identity (primary) with outcome semantics (retry). For paper-1 Phase 1a both retry flags are off by default and this mix is latent; paper-2 M3 ablation aggregators MUST filter on `retry_action_applied == False` for primary-action SR and on `retry_action_applied == True` for retry-effectiveness rollups separately, NOT inspect `action_type` of retry rows as the primary action under audit. A future schema v2.2 bump separating `primary_action_success` / `retry_action_success` is queued as paper-2 prerequisite; paper-1 disclosure-only.

### 3.5.2 Locator-route dispatch — evidence layer and cross-mode scope (A1.25 disclosure)

The locator-route dispatch fix (Cluster 1 patch for B-01/B-02/B-33 family, `p79/envs/locator_dispatch.py`) replaces VWA's framework `mouse.click(union_bound_center)` with Playwright `locator.click()` after a DOM walk-up to find the actionable ancestor (`<a>`, `<button>`, `[role=link]`, `[role=button]`, `<input type=submit/button/checkbox/radio/image/reset>`, `<summary>`, `<area>`, `[contenteditable]`, plus shadow-DOM pierce per B-161). The pre-fix Tier 10 sweep (`scripts/maintenance/probe_tier10_dispatch_target.py`, 2026-04-30) measured 94.4% off-target on failed clicks; the post-fix walk-success-rate per (site, model, mode) cell is computed by `scripts/analysis/aggregate_locator_route_metrics.py` (B-448 added 2026-05-17). Paper-1 reports **two rates** for transparency:

| Site | Model | Mode | Invoked | Walk-success rate (success-conditional ON_TARGET proxy) |
|------|-------|------|---------|---------------------------------------------------------|
| classifieds / reddit × B0 / B1 / Gemma3-VL × dom / som / vision / phantom_* | _to be populated post-Phase-1a clean-rerun, A1.19 + Chunks 2-4 fix wave complete_ |

The walk-success rate is the **success-conditional** proxy for ON_TARGET (we do not have per-step gallery labeling). The unconditional rate is bounded above by walk-success; cases where the walk-up resolver returns null (`walk_fail:no_actionable_within_walk`, etc.) fall back to VWA framework `create_id_based_action()` → `mouse.click(union_bound_center)` = the exact B-33 buggy pattern the locator-route was meant to retire. Paper-1 §4 reports walk-success-rate and walk-fail-rate separately rather than collapse to a single hero number; a future gallery-labeled study would close the success-conditional → unconditional gap, which we leave to follow-up work.

**Cross-mode scope.** Locator-route currently routes (a) DOM/SoM mode id-based CLICK + TYPE actions (full walk-up coverage), and (b) **vision-mode coordinate-based TYPE focus-click** (B-442 fix 2026-05-17 — pre-A1.25 vision-mode TYPE used direct `page.mouse.click(px, py)` which was still B-01-prone; post-fix it routes through `dispatch_coord_based_type` which reuses `_JS_RESOLVE_INPUT` walk-up from pixel coords). Vision-mode coordinate-based CLICK and all framework-fallback hover/clear/upload actions retain the original framework dispatch — `hover`, `clear`, and `upload` action types were verified absent from Phase 1a step JSONL across all conditions (zero observed emissions; the original P79 `dispatch_id_based_hover/clear/upload` functions were deleted as dead code per B-439, retaining only `_JS_RESOLVE_UPLOAD` JS constant as substrate for any future workshop sub-paper expansion).

**Telemetry split — retry-overwrite hole closure (B-440).** Prior to A1.19, the runner overwrote primary action's `locator_route_meta` with the retry step's `next_info` on any step that triggered `baseline_retry_on_no_progress` — the primary dispatch evidence was silently deleted from step JSONL. Cross-baseline asymmetry impact: B0/B1/Gemma3-VL have different retry-trigger rates → biased ON_TARGET denominator. Post-fix the runner stamps two separate fields: `locator_route_meta_primary` (canonical evidence layer, captured before retry block) and `locator_route_meta_retry` (only populated when retry fired). The legacy `locator_route_meta` field retains "value at step write time" semantics for backward compatibility with archive aggregators. `aggregate_locator_route_metrics.py` is B-440-aware and prefers `_primary` when present.

**Schema validator (B-444 nested semantics).** `validate_step_record_v2` at write boundary now type-checks the nested `locator_route_meta*.success` field (must be `bool`-or-`None`, not string) and the `action_kind` enum (must be one of `click | type | type_coord | hover | upload | clear | select_option | None`). Pre-fix `locator_route_meta = {"success": "false"}` (string instead of bool) passed silently — downstream denominator logic treated such records as falsey/truthy depending on implementation, exactly the silent pipeline corruption /stress A1.25 codex Mode B P1-8 flagged. Same nested-semantics check applies to `select_option_meta` (extended in B-480/B-481 to validate `matched`, `match_stage`, `target_type` on all three legacy / primary / retry variants).

### 3.5.3 Observation enrichment surface — `[OPTIONS]` / `[DROPDOWN OPTIONS]` and `select_option` dispatch (A1.25 disclosure)

The observation handed to every baseline mode (DOM / SoM / vision / Phantom-SoM / P-text / P-prompt) is the VisualWebArena accessibility tree augmented by two enrichment passes that run *before* mode-specific dispatch in `p79/envs/vwa_wrapper.py::_to_p79_obs` (lines 980-1033). `_inject_select_options` queries the live page for `<select>` elements, matches each combobox node from `obs_nodes_info` to the nearest `<select>` within `_INJECT_DISTANCE_NATIVE_SELECT_PX = 100 px`, and appends an `[OPTIONS]` (or `[OPTIONS: currently selected="X"]`) annotation after the combobox line. `_inject_css_dropdown_options` performs the same nearest-AXTree-node match for hidden `<ul>` menus (CSS custom dropdowns; e.g. classifieds "Sort by" `<span class="see_by">`, reddit sort `<button class="dropdown__toggle">`), within `_INJECT_DISTANCE_CSS_DROPDOWN_PX = 150 px`, and appends `[DROPDOWN OPTIONS]` lines. This is **standard VisualWebArena agent practice**: the upstream model interface cannot directly observe hidden `<ul>` or `<select>` options, so every published VWA agent (including state-of-the-art systems such as Aviator-Web) augments the observation at the wrapper layer rather than relying on the agent to physically click each dropdown to enumerate options. Phantom-SoM / P-text inherit the enriched AXTree via the canonical `build_som_text_from_obs_text` builder in `p79/experiment/som.py:96-144`, which re-attaches the `[OPTIONS]` / `[DROPDOWN OPTIONS]` lines under their owning `[id=N]` mark (the `_options_map` pass at `som.py:125-143`). Vision mode discards the enriched text payload entirely (`som.py:307-327` returns `som_text=""`) because the action schema for vision is coordinate-based — vision agents resolve options by clicking the dropdown trigger and reading the resulting screenshot. Empirical enrichment coverage on the archive run `B1_phantom_prompt_classifieds_20260501/` (3 069 step records, `observation_dom.txt` artifact spot-check) is 77.6 % of observations carrying at least one `[OPTIONS]` or `[DROPDOWN OPTIONS]` annotation (`[DROPDOWN OPTIONS]` 40.4 %, `[OPTIONS]` 37.8 %, both 0.6 %); the remainder are pages with no dropdown affordance. Paper §1 cost comparisons (DOM vs P-text vs Phantom-SoM) operate on the same enriched AXTree across baselines, so this enrichment does not bias the within-baseline cost-delta claim; the cross-mode vision-vs-text comparison is interpreted under the action-schema asymmetry already disclosed in §3.5.1 rather than as an enrichment effect.

The `select_option` action dispatches against this enriched view via `vwa_wrapper.py:543-714`, with two paths: (a) element-id (DOM/SoM/Phantom modes) that uses `obs_nodes_info` pixel coordinates + `document.elementFromPoint` to locate either a native `<select>` or a CSS dropdown trigger, and (b) coordinate (vision) that takes the model-emitted `[x, y]` and applies the same `elementFromPoint`-based resolution. Both paths run a three-stage fuzzy matcher `_FUZZY_MATCH_JS` (`vwa_wrapper.py:41-73`) over the candidate options: exact text equality → case-insensitive equality → keyword-overlap heuristic (`bestS ≥ 2` keyword matches with prefix-length-4 partial credit). The fuzzy tier is a **runtime soft contract** that relaxes the prompt-level "option_label must match the visible option text exactly" requirement (`p79/agents/_shared_vl_utils.py:113-116, 184-187, 297-300`); we keep it because the alternative — a 0 % success rate when the model paraphrases ("Sort by Price" instead of "Lower price first") — would dominate the cost-of-mistakes term in paper §1 and obscure the comparative claim. We disclose rather than disable: the post-B-481 evidence layer (B-482 aggregator) reports `match_stage ∈ {exact, ci, fuzzy, index, none}` per (site, model, mode) cell so reviewers can audit fuzzy-tier share and confirm cross-baseline interpretability of the action schema.

**Evidence layer (B-481 + B-482).** The pre-fix `step_record.select_option_meta.success` field was overpromised: the JS dispatch wrote `return;` for no-match / wrong-coordinate / no-label / successful-click alike, and the Python side stamped `success=True` whenever `page.evaluate()` did not raise — exactly the same class of silent-pipeline-corruption that the B-440 locator-route split closed. Post-fix the JS returns a structured payload `{matched, match_stage, target_type, selected_text_before, selected_text_after, clicked_text, error}` and the Python side populates `select_option_meta` accordingly, with `success` now meaning "an option was matched and dispatched" (semantic alignment, not breaking rename: legacy aggregators reading `success` get a tightened, more accurate signal). Three independent /stress audits caught this hole within 6 hours (parallel-session A1.4 codex Mode B as B-453, plus this session's Mode A + Mode B). `aggregate_select_option_dispatch.py` (`scripts/analysis/`, B-482) computes per-cell ON_OPTION rate and fuzzy-tier share; archive rows that predate B-481 are surfaced under `pre_b481_unknown_matched` so operators can quantify the legacy-semantics share in any aggregated number.

**Cross-mode `[DROPDOWN OPTIONS]` ↔ `select_option` schema alignment (B-483 prompt update).** The pre-A1.25 action-schema prompts said `select_option` is "for `<select>` dropdown elements only", but the wrapper exposed CSS custom dropdowns under `[DROPDOWN OPTIONS]` annotations and accepted `select_option` against them (via the CSS-menu fallback in `vwa_wrapper.py:618-647 / 684-713`). Action-choice statistics on such steps were not interpretable as schema-compliance — a model following the prompt literally would click the CSS trigger rather than dispatch `select_option`, while a model that ignored the prompt could exploit the undocumented path. Post-fix the three shared prompt blocks now read "Use for native `<select>` dropdowns and for custom dropdowns/menus annotated with `[DROPDOWN OPTIONS]` under their trigger" so the action-schema matches the runtime affordance.

**CSS dropdown injection multi-menu accumulation (B-479).** Pre-A1.25 the injection dict `injections[best_eid] = dd['options']` overwrote, losing all but the last menu when multiple hidden `<ul>`s clustered near one trigger (classifieds + reddit nav pages with main + breadcrumb menus). Post-fix `injections: defaultdict(list)` accumulates, and the renderer emits one `[DROPDOWN OPTIONS]` line per accumulated menu so the agent sees all clustered options.

**Cross-benchmark generalizability — deferred to follow-up workshop paper.** The above is paper-1 §3 methodology disclosure for VisualWebArena-classifieds + VisualWebArena-reddit; the cross-benchmark generalizability of the enrichment surface (whether `[OPTIONS]` / `[DROPDOWN OPTIONS]` / fuzzy-match assumptions hold on WebArena, AgiSDK, or future benchmarks) is deferred to a follow-up workshop paper specifically targeting GRL design across benchmarks.
