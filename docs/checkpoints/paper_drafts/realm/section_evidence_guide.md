## Reading guide

**Tables 1–5 — what each mode achieves, and whether the six collapse into three.** Table 1 is the raw success rate. Tables 2–3 group the six modes into the three shapes web agents actually ship in, and Table 5 is the licence for that grouping: over 26 metrics the four image-free modes are never the extreme in ≥7 of 8 cells, so they do not behave differently enough to keep apart. The grouping produces two facts: `vision-only` is never the sole best class (hybrid 4, no-image 3, one tie), and which class wins reverses between benchmarks — on `WA·B0` no-image leads hybrid by 13.46pp. **The trap is in Table 4**: dropping the whole no-image class costs far more than dropping the others, but it has four arms against one each. The arm-matched columns beside it show no systematic difference (no-image 4x, vision-only 3x), and those are the ones that compare like with like.

**Tables 6–9 — the full behavioural matrices.** Every metric, every cell, every mode, unsummarised: Outcome, Macro (what the agent did), Micro (how often what it did failed), Efficiency. These are the substrate the consistency counts in Table 5 are computed from, included so a reader can check a claim rather than take the tally on trust. Two columns are gates rather than measurements and are marked as such: `loc-fallback` is near-zero for Vision because there are no element ids to fall back from, not because it fails less.

**Tables 10–12, 15, 38–39 — efficiency, and the denominator nobody declares.** Table 10 shows the cost and latency orderings are not each other restated. Table 15 changes the denominator from per-attempt to per-success and the cheapest mode changes in 4 of the 6 cells that carry enough successes to divide by. **Every pairwise interval overlaps**, so this supports 'the denominator must be stated', not 'X is more efficient'. The other three say the same thing about three different quantities: Table 11 — a latency figure is mostly browser and container, not model, and stripping them changes which mode is fastest; Table 12 — each efficiency quantity admits a defensible alternative definition that reorders the modes; Table 38 — B0 pays an API bill and B1/B2 pay electricity, and those are not the same quantity. Table 39 splits the cost figure the way Table 11 splits the latency one, and finds the protocol-repair share differing several-fold between model families on the same tasks. **The pattern, not any one row, is the finding: efficiency here is estimand-dependent and the estimand is usually left implicit.**

**Tables 16, 18–19 — is a second representation worth buying?** Table 18 is the upper bound on the whole question: what a perfect per-task choice could reach, and — in the same row, deliberately — what adding one arm or rerunning one arm buys instead, because the ceiling column is a six-arm union quoted against a one-arm baseline. Its second ceiling, *same tasks solved at lower cost*, is the one no arm-count objection reaches, since it adds no arms. Table 16 asks whether the fused mode beats the single channel that suits the workload: it does not, in any of 8 cells. The comparison is against a **measured rerun band**, not against zero, because the question a deployment asks is whether a new arm beats re-running the arm it already has — Table 19 puts those two side by side at the same arm count. **The trap is the band's width, not its coverage**: only two cells carry a measured floor at all, and one standard deviation of the null it is drawn from is of the same order as the band itself, so 'clears the band' is not 'clears the noise'. Since 2026-08-03 the fused arm is no longer extrapolated onto — the SoM replicate landed and its own floor falls inside the band.

**Tables 17, 20–24, 29, 35 — five ways of routing, and what each one dies of.** Table 17 finds a signal that is as good as signals get: a regex over the task intent, costing nothing and needing no episode, that flags tasks where the screenshot is worth +22.54pp against +0.65pp elsewhere. Table 20 turns it into a policy and it **still loses to always-Vision**, because the screenshot does not hurt on the unflagged tasks either. Table 21's cascade beats always-rich at no operating point — but Table 22 is the table that says what that means: against the *same budget spent at random* the confidence ranking wins nearly everywhere, so the signal is informative and still not enough. Table 23 adds the benchmark's own difficulty annotation for a mean ΔAUROC of +0.0024. Table 24 shows the feature a practitioner would reach for first does not separate what it appears to. Table 35 pools the backbones and routes by cost tier instead of by task. Table 29 is the supervision problem underneath all of them: the rows a router would learn from are the contested ones, and those are exactly the rows that flip between two runs of the same condition. **The pattern is not 'no signal'** — it is that the arm the router would route *to* is already the right arm to route everything to.

**Tables 25–28, 32–34, 36 — where the failures come from.** Table 25 is the headline cut with both sides in one table, so the asymmetry is visible without flipping between floats; Tables 26–27 are the same data split per side at full depth. These are the paired cut: on tasks only one channel solved, how did the other fail? Those count rule hits, so Table 28 asks the same question without the rule vocabulary — six probes read straight off the step records — and finds the losing channel failing *more blandly* there than elsewhere, which is what closes the objection that the residual is an artefact of a VWA-shaped ruleset. Table 32 decomposes the DOM→P-SoM transition into a text axis and a prompt axis, and Table 33 asks whether that text axis moves per-step decision quality more than it moves macro action frequencies. Table 34 counts hallucinated element references — inapplicable to Vision by construction, marked. Table 36 corrects a false-positive in the page-change detector. **Caution:** **A per-rule frequency is a distribution of symptoms, not of causes.** The two largest rows in most cells are risk markers that causal verification did not confirm as death causes.

**Tables 13–14, 30–31, 37, 42 — what would make all of the above wrong.** Table 37: the evaluator emits two values, so there is no graded target and every routing negative inherits that. Table 14: the replicate inventory behind every stability figure here is one cell, so those bands are what repetition happened to deliver, not bounds on what it could. Table 13: an arm's measured ceiling is partly this harness — Vision is on the coordinate path by construction, and that path succeeds far less often than the element-id one. Tables 30, 42: 6 successes were credited by accumulated site state, and zeroing them flips 1 verdict. Table 31: reddit episodes leave the benchmark for the public internet on 1.05–2.13% of steps against 0.16% on classifieds, and reddit's container is slower than classifieds' before any agent behaviour enters.

**Tables 40–41 — inside the model, and how far that gets us.** Everything above is behavioural. These two ask whether the representations differ *in the residual stream* and whether that difference is used. Table 40: every mode pair is perfectly separable by a linear probe, at cosine gaps in the third decimal — present and readable. Table 41: patching the prompt-family signature from one mode into another moves the output, but the honest column is **convergence toward the source**, not displacement — random injection maximises displacement by destroying the continuation. **The trap is the second control**: a source drawn from an unrelated task converges almost as well, so the content-specific reading rests on the layer profile (mid-stack for the real arm, boundary layer for the shuffled one) rather than on the size of the effect. These are one backbone, 24 tasks, one decode step, and the mechanism programme was shelved 2026-05-14 — they are here because a shelved result and an absent one look identical on disk and are not the same thing to a reader.
