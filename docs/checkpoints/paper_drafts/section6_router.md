### 6.1 Setup — Within-cell 5-fold CV deployment

We evaluate the **learned router R_P2** on the phantom routing space via Phase 1a Pass-2 fire across 6 (baseline, site) cells = {B0, B1, B2} × {classifieds, reddit}. Pass-2 reuses the Pass-1 baseline task pool (cls 0-233 / red 0-209) but evaluates each task through a **fold-aware predictor**: at training, each site's task universe is split once into 5 folds (plain `KFold`, shuffle, seed=42) and that **single per-site fold map is shared by all three model cells of the site** (B-1871) — same-site cells therefore agree on every task's fold. At deployment, each task receives its prediction from the LR head trained on the fold where the task was held out, ensuring no in-sample memorization between training and runtime evaluation. The per-site shared map is what makes the Stage-2 feature machinery leak-free at *task* level: a task held out in fold k has **all** its rows (across the site's three baselines, which share verbatim-identical intents) excluded from fold k's vectorizer/MI selection pool, not merely the row of the cell under evaluation. Folds are deliberately unstratified — same-site cells have different per-cell oracle labels, so no canonical stratification label exists; fold balance is delegated to the B-995 min-class filter and Stage-3 degenerate-fold guards. Cell-constant features (site, capability tier) are EXCLUDED from the per-cell LR input space — cell identity is implicit via the runtime pickle selected per (baseline, site).

**5-Stage pipeline**:
1. **Stage 1 deterministic raw extraction** (`scripts/analysis/extract_50_features.py`): 5 numeric features (`dom_complexity`, `text_length`, `tokens_input_text`, `intent_token_count`, `reasoning_difficulty`) + 15 binary features (`has_reference_image` + 14 intent regex banks: color / search / compare / nav / filter / sort / aggregate / compose / form_fill / account_action / visual_attribute / question / action_word / temporal).
2. **Stage 2 global fold-local pooled MI selection** (`scripts/analysis/train_l1_router_with_mi.py`): for each fold k ∈ {0..4}, pool = all task indices except union of all 6 cells' fold-k holdouts (pool size ≈ 1124 of 1404 total tasks). Fit `TfidfVectorizer(max_features=30, min_df=3, stop_words='english')` on pool intents → 30 TF-IDF columns. Concatenate with 5 numeric + 15 binary → 50-dim design matrix. Fit `SelectKBest(mutual_info_classif, k=18)` on pool to select top-18 features. Dump 5 vectorizer pickles + 5 selected_idx JSON.
3. **Stage 3 per-(cell, fold) LR training** (`scripts/analysis/train_l1_router.py`): for each cell × each fold (= 30 combinations), apply B-995 min-class-n=10 filter (drop classes with <10 train-fold samples to prevent minority hallucination), build design matrix using fold-k vectorizer + selected_idx mask, train `Pipeline(StandardScaler + LogisticRegression(class_weight=None, C=1.0, max_iter=2000))`. Dump 30 pickles + 6 per-cell meta JSON with thresholds-per-fold dict.
4. **(b) Inner-CV τ tuning**: within each (cell, fold) outer fold, run inner `StratifiedKFold(5)` on the train fold, evaluate the confidence-threshold rule at candidate τ ∈ {0.3, 0.4, 0.5, 0.6, 0.7}, pick τ* maximizing inner-holdout **mode-match accuracy** (decided mode == oracle label — a proxy for Pareto utility, NOT true SR, per `train_l1_router.py:187`; tie-break = highest τ for conservative routing). τ never tuned on outer holdout.
5. **Runtime fold-aware prediction** (`p79/policies/learned_router.py::predict_mode_fold_aware`): at Pass-2 fire, lookup `fold_assignment[task_id] = k`, load the corresponding fold-k vectorizer + selected_idx + LR pickle + τ_{C,k}, apply `pipeline.predict_proba(features)`, route to `argmax_mode` if `max_prob > τ_{C,k}` else fall back to `phantom_som` (B-998 confidence-threshold fallback rule, B-995 safe routing under low confidence).

### 6.2 H10 Pareto non-dominance operational deployment gate (two-layer)

**Estimand (preregistration §H10 OPERATIONAL DEPLOYMENT GATE, locked 2026-05-18 per /stress A2.8 P0-2-AB* + P0-3-A* + P0-1-A* user-directive resolution)**: per cell, the router achieves a (Cost, SR) operating point. Two-layer criterion:

- **Cell-level (statistical)**: paired bootstrap (B=1000, seed=42) on the cell's common task set; cell **passes cell-level** if router is Pareto non-dominated by any of the 5 pre-registered single-mode baselines {DOM, SoM, Vision, P-text, P-SoM} in ≥95% of bootstrap replicates (P-prompt excluded per prereg §H10 baseline anchor row; expands to 6 if Phase 1a B0+B1+B2 cls produce ≥50 ep P-prompt outcomes). Per-cell test is task-level paired bootstrap *within* the cell — per-task pass/fail labels are the resampled unit, not cells across the grid.

- **Grid-level (operational robustness criterion)**: H10 is **considered deployable** iff at least **5 of 6 pre-registered cells pass cell-level**. This 5/6 threshold is a **fixed-cell operational deployment criterion** for paper §6's deployability claim — NOT a binomial significance test over a population of cells. The 6 cells are the complete pre-registered decision family per decision "3A" finite-population framing (prereg §2 H1 estimand); the prereg does not interpret 6 cells as a random sample from a larger universe, so a binomial inference over cells (K=5/6 at α) is not a coherent frequentist test at this design. The §2.4 K-of-N fake-precision retirement doctrine targets across-cells binomial inference at α (which inflates Type-I error at small N); this 5/6 threshold is an *operational engineering deployability margin* not interpreted as a frequentist test (no across-cells α, no Type-I/Type-II coupling).

**Operational gate verdict**: K cells pass cell-level / 6; **H10 deployable** iff K ≥ 5. Failing the operational deployment gate does NOT constitute a statistical rejection of any null hypothesis at α=0.05; it characterizes the router as not robust enough across the pre-registered grid for paper §6 to claim deployable learned routing — paper §6 under H10-FAIL reports per-cell descriptive + Appendix-D FE pool, R-rule branching applies (R3 cap if H10 FAIL alone, R5 if H1 also fails). *(Amendment 02, 2026-05-23: R5 still fires on H1-failure, but the post-R5 reporting scope is conditional on H3/H10 — the "H10 passes after H1 fails" case is Route C'-R, a lower-claim router/systems pivot that does NOT claim confirmed phantom-space structure; see `docs/prereg_amendments/AMENDMENT_02_GATE_LADDER_20260523.md` §4.)*

### 6.4 Site-asymmetric viability finding (paper §6 main narrative)

The cell-level (Cost, SR) Pareto non-dominance breakdown across the 6 pre-registered cells is the load-bearing narrative for paper §6. The following is a **pre-registered directional hypothesis stated before Phase 1a fresh data** (per preregistration §H10 pre-hoc theoretical prediction — NOT archive-simulation-derived per /stress A2.8 P0-3-A* 2026-05-18); every clause is to be replaced by a measured verdict once the §6.2 table fills (all entries currently TBD), and is written in the conditional accordingly:

- **Visual-rich sites (classifieds)**: learned routing is *hypothesized to* exhibit Pareto non-dominance over best-single-mode; the classifieds task distribution *would* provide mode-asymmetric structure (color + visual-attribute tasks → phantom_som; navigation → DOM) that an 18-feature LR could distinguish from intent text. Whether the strictly-better diagnostic (§6.6) also fires — not non-dominance alone — is the actual deployability test.
- **Text-dominated sites (reddit)**: the learned-routing prediction distribution is *expected to* collapse toward majority-class prediction (≈ always_phantom_som baseline); per-cell Pareto non-dominance, if it holds at all, *would* hold only marginally. Forum-style thread-traversal tasks are *not expected to* benefit from `[SOM_MARKS]` flat representation over hierarchical AXTree (the two-knob "forum lookup → flat list" prediction would then be refuted on reddit task character — reddit tasks span navigate-and-discuss workflows, not pure list-lookup).

If borne out, this site-asymmetric pattern *would be* **paper-grade interesting**: not "router works/doesn't work" but "router viable conditional on site task-distribution heterogeneity". Such a result *would* support the **representation-axis routing hypothesis** while bounding deployable applicability to visual-rich web settings. Phase 1a fresh data is the falsification test (see the Falsifiability note below).

### 6.5 Intelligent-baseline ladder (B-1006 R5 reviewer-defense)

Beyond random Tier-0a/0b/0c baselines (preregistration line 199 line 204), we report **4 intelligent baselines** to bound the learned router's lift from above and below:

1. **Always-cheapest-mode** (cost-only baseline, = always-DOM in current 5-arm set): bounds router's "cost-aware" claim from cost-axis side.
2. **Decision-stump single-feature** (e.g. `if DOM_tokens > 10K → route P-text else route DOM`): bounds router's feature-set value over a 1-feature heuristic.
3. **Per-task-lookup-table** (∞-capacity reductio = LR with task_id one-hot feature): bounds router from above — the 18-feature LR's generalization headroom equals (per-task lookup SR - 18-feature LR SR), quantifying how much "feature-conditioned routing transfers beyond memorization".
4. **LR-DOM-features-only** (intent regex + browser state, no TF-IDF ablation): bounds router from text-feature side.

These intelligent baselines address the R5 reviewer attack "router learns noise vs signal" — the per-task-lookup reductio in particular provides an ∞-capacity ceiling that any feature-conditioned router must remain below.

### 6.6 Limitations and disclosure

- **Within-population evaluation**: paper §6 results are within Phase 1a cls + red task pool. Phase 1b shop fire (post-workshop submission) provides the genuine cross-site out-of-distribution test for the routing claim.
- **5-arm baseline set**: P-prompt excluded due to cls archive aborted at 4 ep; expands to 6 if Phase 1a B0+B1+B2 cls produce ≥50 ep P-prompt outcomes.
- **τ candidates pre-locked**: {0.3, 0.4, 0.5, 0.6, 0.7} fixed before Phase 1a fire; not exhaustively grid-searched.
- **2-site meta pool**: K-of-6 = 2 sites × 3 baselines; cross-site generalization claim limited per §8 limitations 2-site disclaimer (B-1007).
- **Confidence-threshold fallback rule (not a cost-weighted objective).** Routing uses `max_prob > τ` thresholding (B-998 (a) path); τ is tuned by inner-CV **mode-match accuracy** (decided mode == oracle label), a proxy for Pareto utility — **NOT** true SR or an explicit cost-weighted objective (`train_l1_router.py:187` flags this explicitly). An explicit cost-weighted objective `SR̂ − λ·Cost` is deferred to follow-up (Phase 1b shop fire scope). The per-cell LR uses `class_weight=None` (B-995 fix dropping the prereg's "balanced" reweighting that produced minority hallucination); the §H10 prereg text still reads "balanced" and is pending alignment.

> **Draft status (S3-audit prose 2026-06-02, /stress-revised §312)**: the caveats below were surfaced by the S3 3-AI audit (实验笔记 §311) and rewritten after a second 3-AI /stress pass (§312, codex+gemini) that judged the first draft as *amplifying* rather than defusing reviewer attacks. They are estimand/inference disclosures at workshop scope; none changes locked code or the §6.2 gate.

- **H10 non-dominance is a pre-registration compliance gate; the deployability claim rests on strictly-better.** §6.2's Pareto non-dominance test is the pre-registered (locked 2026-05-18) operating-point gate, reported for compliance. But non-dominance proves only "not worse", and on low-success cells it is **structurally uninformative**: the min-class-n=10 filter (B-995) drops most modes from the trainable label set, forcing the per-cell head toward a constant fallback (phantom_som), and because phantom_som sits at the cost frontier (cost ≈ DOM by construction, §3) that fallback is non-dominated trivially. We therefore treat `k_cells_router_strictly_better` (cells with θ = SR_router − max-feasible-baseline-SR bootstrap-CI lower bound > 0; `aggregate_h10_pareto.py:371,747`) as the **mandatory marginal-utility diagnostic**: a cell passing non-dominance but not strictly-better supports a "non-dominated operating point" statement only — **not** a "learned routing benefit" claim. We do not tighten the §6.2 gate itself (a locked-estimand change deferred to the main-conference submission), but no §6 deployability claim rests on non-dominance alone.
- **Two B0 cells carry a serving-noise floor that can exceed their routing margin.** B0 reaches the model through an AWS proxy with ~13.3% per-task SR discordance under same-payload replay (实验笔记 §308). The §6.2 per-cell paired bootstrap resamples tasks within one run and is blind to this run-to-run floor; for a B0 cell whose non-dominance margin is below 13.3%, the pass/fail outcome cannot be reliably distinguished from serving noise, so we report those cells descriptively (floor annotated) and rest no rigorous deployability claim on them. Replicate-run calibration is deferred to the main-conference submission (§D4).
- **Oracle labels use a prior cost ordering that measured cost does not support.** The per-task oracle label is the cheapest *successful* mode, where "cheapest" uses a prior mode ordering (`router_features.py:90,166`), not measured cost. On the archive B0-classifieds sanity set the measured total-billed cost is near-flat (≈11.7% spread) and the empirically cheapest mode is `vision` (0.0648), not DOM (0.0696) — the prior ordering does not merely lose precision, it mis-ranks the frontier. Because costs are near-flat, re-deriving labels from measured cost would likely re-scramble the label distribution rather than shift it at the margin; we do not characterize that magnitude here and defer measured-cost re-labeling — with a prior-vs-measured label-flip-rate sensitivity table — to the main-conference submission. (The router's label space spans the **six** `MODES` incl. phantom_prompt, one more than the five-arm H10 baseline set; this is a deliberate asymmetry — label space = what the router predicts, baseline set = what it is judged against — flagged here to pre-empt a hidden-mismatch reading.)
- **On low-success cells the router is a majority-class baseline, not a learned boundary.** Each per-cell LR head trains a multinomial on one cell's success-conditional tasks across four folds; at the observed success rates the trainable per-fold sample is small and the min-class-n=10 filter (B-995) frequently reduces the effective label set to one or two modes, so on low-success cells the head is a **static majority-class predictor**, not a learned router — §6 on those cells describes a static fallback heuristic. The per-task-lookup ∞-capacity reductio (§6.5) bounds the headroom a larger-sample regime could add. (We avoid a specific per-fold sample count pending Phase 1a fresh data — on-disk H10 artifacts are still no-data placeholders.)

### 6.8 Positioning among efficiency-routing methods (representation vs compute axis)

> **Draft status (S4-prose 2026-06-02, 待 stress)**: This positioning subsection integrates four cost/efficiency-routing neighbors (lit note `docs/literature/cost_routing_neighbors_2026-05.md`, 实验笔记 §310; bib keys verified via arXiv API). It has not yet passed the `/stress` gate. An editor may prefer to move this subsection ahead of §6.6 (Limitations); it is appended here to avoid renumbering the v0 placeholder.

Efficiency routing for LLM agents has, to date, acted on **compute**. The model-routing line chooses *which model* answers under a cost-quality tradeoff — FrugalGPT's API cascade \citep{chen2023frugalgpt}, RouteLLM's preference-learned router \citep{ong2025routellm}, the uncertainty-decomposition router of \citep{peale2026flexibleRouting}, and the streaming cost-sensitive variant \citep{shirkavand2025cscr}. PANDO \citep{li2026pando} adds a *capacity* split inside a single VisualWebArena agent (an expensive planner versus a cheap actor) on top of keyword-retrieved skills. DMR \citep{li2026dmr} routes *numeric precision* (a bf16 versus a W4/W3-quantized variant of the same model) per step. ReVision \citep{abaskohi2026revision} routes the *visual-token budget*, dropping temporally-redundant image patches. Early-exit halting \citep{lu2025earlyexit} routes *when to stop* within an episode. Every one of these holds the observation representation fixed and varies the amount or kind of computation spent on it.

Our learned router fills the orthogonal axis: it holds the model, the precision, and the compute budget fixed and varies the **observation representation** — the same browser state rendered as a hierarchical AXTree (DOM), a marked SoM bundle, or a flattened `[SOM_MARKS]` text list — selecting per task from intent features alone.

| Method | Routes (per step/task) | Axis | Base / benchmark |
|---|---|---|---|
| FrugalGPT, RouteLLM, CSCR \citep{chen2023frugalgpt,ong2025routellm,shirkavand2025cscr} | which model | compute | API model cascades |
| PANDO \citep{li2026pando} | model capacity (planner vs actor) | compute | VWA / Opus 4.6 + GPT-5.2 |
| DMR \citep{li2026dmr} | numeric precision (bf16 vs quant) | compute | ALFWorld + WebShop / Qwen3-1.7B/4B |
| ReVision \citep{abaskohi2026revision} | visual-token budget | compute (input size) | OSWorld / AgentNetBench / WebTailBench / Qwen2.5-VL-7B |
| Early-exit halting \citep{lu2025earlyexit} | when to stop | compute (horizon) | embodied / 4 LLMs |
| **This work** | **observation representation (DOM / SoM / phantom)** | **representation** | **VWA cls + red / Qwen3-VL 4B & 235B + Gemma-3-4B** |

Two of these neighbors sit close enough to require explicit differentiation.

**DMR — closest per-step routing precedent and method anchor, but routes precision not representation.** DMR is the nearest *per-step routing* precedent in the literature and shares B1's backbone family (Qwen3-1.7B/4B). Two of its ideas transfer to our router as registered future upgrades (§6.6): (i) its routing signal — the *action-distribution KL between a cheap and an expensive variant* — is a concrete alternative to our static per-task TF-IDF + logistic-regression classifier, suited to a per-step phantom-routing extension; and (ii) its KL-supervised-then-GRPO-refine training recipe is a natural upgrade path for that extension. But DMR routes the *precision* of a single model under a fixed representation, whereas we route the *representation* under a fixed model; it is therefore a method analogy and a precedent for per-step routing, **not a baseline** we run against.

**PANDO — closest VWA-efficiency neighbor; differentiate hard.** PANDO is the closest published work on "efficiency in VisualWebArena," and three differentiators keep it from being confused with our contribution. (i) **Routing object.** PANDO's hierarchical routing is model-capacity (planner vs actor) and its skill *selection* is deterministic keyword containment; neither is representation routing — we route the observation representation, the open axis. (ii) **SR is not comparable.** PANDO's base is a frontier closed stack (Claude Opus 4.6 planner + GPT-5.2 grounding); its 58.3% SR must never be tabled next to our 4B open-model SR (B1/B2). (iii) **The cost lever is small in PANDO.** Its routing + compression + cache ablation adds only +1.7pp SR (its skills do the SR work, +18.7pp), so PANDO is a *narrative ally* for "routing lowers marginal cost," not evidence for our (constructed, §1) cost ≈ DOM. We do, however, borrow three of its trajectory-level efficiency instruments for our §4 / §6 reporting — Action Repetition Rate (which aligns with our runner cycle detection), Step Overhead Ratio, and Prompt Cache Utilization — and its critique of WALT for excluding pre-evaluation discovery cost corroborates our total-billed canonical estimand (§3.5).

ReVision and Judge Circuits inform adjacent claims rather than the router directly: ReVision \citep{abaskohi2026revision} is the visual-redundancy contrast positioned in §2.4 (it requires fine-tuning the backbone, so it is a contrast point and not a method we reuse), and Judge Circuits \citep{feldhus2026judgecircuits} supplies the mechanistic motivation for why the representation axis is load-bearing (§2.3, §7.4). The one-sentence synthesis: **prior efficiency routing acts on compute — which model, which capacity, which precision, which visual-token budget, when to halt — while we route the observation representation, the unfilled axis, which circuit-level evidence on the same backbones suggests carries separable, format-conditional computation.**
