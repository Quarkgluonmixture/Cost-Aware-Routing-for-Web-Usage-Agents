# 证据层查缺补漏 — 零预设审计 prompt

用途: 新 session 独立审 P79 证据层, 找出该进没进 / 进了少了 / 进了错了 / 不该进 / 没算但有用。

**为什么零预设**: 上一个 session 刚做完一轮大改, 如果把它的结论写进 prompt, 新 session 会顺着
验证而不是独立发现 —— 而恰恰是"顺着已有结论走"让三个 frame 在三天里连续立不住。所以下面**只给
入口和方法, 不给任何结论**。

**给新 session 的话**: 直接把 `---` 以下整段贴进去。

---

审 P79 这个项目的证据层。目标不是理解它说了什么，而是**找出它哪里不完整、哪里错了、哪里多余、
哪里漏算了本可以算的东西**。

## 先读什么

```
docs/analysis/cross_sites/           34 个产物 (*.md + *.json 成对)
docs/analysis/cross_sites/EVIDENCE_LAYER_SUMMARY.md    汇总/覆盖地图
docs/checkpoints/paper_drafts/realm/                   当前论文骨架
scripts/analysis/export_ablation_tables.py             把产物渲染成 30 张表的生成器
scripts/analysis/                                      产生上述产物的脚本
```

⚠️ **不要读 `docs/checkpoints/实验笔记.md`**（2.4 万行编年史）。它会把上一轮的结论直接灌给你，
你就不再是独立的了。要查"这个量是不是已经测过 / 这个决定是不是已经裁定过"，用防重做台账：

```bash
.venv/bin/python3 scripts/maintenance/known.py <关键词>
```

台账每条都带 `caveats` 和作废标记，而且是**事实**不是叙事。允许并且鼓励用它。

## 回答这五个问题，每个都要给证据

**① 该进没进** — 仓库里算出来了、但没进汇总也没进表的东西。
怎么找：把 `docs/analysis/cross_sites/*.md` 的文件名逐个 grep `EVIDENCE_LAYER_SUMMARY.md` 和
`export_ablation_tables.py`。没被提到的就是候选。对每个候选，读它的产物判断它是**有实质结论**
还是**索引/中间件/已被取代**。

**② 进了但少了** — 进了汇总或表，但只用了它的一部分。
怎么找：对每个已引用的产物，比较它的 JSON 里有多少字段 vs 表里用了几列。特别注意只放了汇总
统计（计数、均值、tally）而原始矩阵没放的。

**③ 进了但错了** — 数字不对、口径不对、或者结论跟数据不一致。
怎么找，三个具体动作：
- **同一份产物内部自相矛盾**：md 里的散文说的和同一份 md 里的表说的对不上。
- **产物与生成它的脚本不一致**：脚本里写死的字符串（分母、计数、"X 在 N/M 格成立"这类句子）
  和脚本自己算出来的值对不上。查法：在 `scripts/analysis/*.py` 里 grep 硬编码的数字与比例。
- **表与产物不一致**：`export_ablation_tables.py` 读的 JSON 字段是不是它以为的那个。
- **阈值没跟着分母走**：如果一个判据原本是 "≥5/6"，在 8 格上正确的等价物是 ≥7/8（83%）而不是
  ≥5/8（63%）。凡是分母变过的地方都查一遍。

**④ 不该进** — 进了汇总/表但撑不住的。
怎么找：读每张表的 caption 和每条 claim 的限定语，问三件事 —— 样本量够不够（成功数是个位数的
格子能不能承载结论）？是不是 oracle（事后知道答案才成立）？被比较的各臂之间判据是不是同一个
（有没有把"结构性不适用"当成"测出来是零"）？

**⑤ 没算但有用** — 数据在磁盘上、但没人算过的量。
怎么找：`results/` 下有哪些字段被记录了却没有任何产物读它。
`grep -rl "<字段名>" scripts/analysis/` 返回空的就是候选。然后判断它能回答什么问题。

## 三条纪律

1. **每个发现都要能被复现**：给文件路径 + 行号 + 复现命令。"这个看起来不对"不算发现。
2. **区分「没测」和「测出来是零」**：一个规则在某个模式上不适用（缺少它依赖的字段）和它测出来
   是 0，在表格里长得一模一样，但含义相反。凡是 0 都要问一句它是哪种。
3. **不要相信任何一句"在 N/M 格成立"，先自己数一遍**。

## 交付

一份 markdown，五节对应五个问题。每节按**严重度**排序，不是按发现顺序。每条给：

```
- [严重度] 一句话说清是什么
  证据: <路径:行号 / 命令 / 数字>
  影响: 它让哪条 claim 站不住, 或者它能支撑哪条新 claim
  成本: 修/补需要多少工作 (小时级 / 天级 / 需要跑实验)
```

最后加一节 **"我查了但没问题的"** —— 列出你验证过且确实成立的部分。一个只报坏消息的审计无法
判断覆盖率。
