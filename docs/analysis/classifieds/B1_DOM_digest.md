## 三、AXTree 信息可达性分析

基于 `digest_enrich.py` 对 217 条失败 episode 的原始 step 日志和 artifact 进行确定性分析。

### 3.1 商品描述文本不可达

| 指标 | 数值 | 含义 |
|------|------|------|

## 四、脚手架 / 表征结构性缺陷（118 例，54.4%）

### 4.1 视觉/图片信息不可达（99 例，占脚手架问题的 91%）

这是 DOM 模式最大的结构性瓶颈。纯 DOM 环境无法获取图片、颜色、视觉属性等信息，导致大量任务在结构上不可完成。

**表现形式**：
- **目标不可达**（47 例）：任务要求匹配视觉属性（颜色、款式、图片内容），DOM 中不含图片语义，agent 无法验证候选商品
- **执行停滞**（12 例）：agent 知道需要视觉确认但无法获取，在页面上反复滚动
- **搜索循环**（11 例）：因无法从视觉确认目标，agent 反复用不同关键词搜索同一目标
- **导航循环**（10 例）：反复进出详情页试图"看到"图片信息，形成 click-back 死循环
- **视觉属性 DOM 不可达**（9 例）：颜色、外观等视觉属性在 DOM 中完全缺失
- **过早结束**（6 例）：agent 判定视觉信息不可获取，直接放弃任务
- **事实推理/答案对齐错误**（4 例）：无法看到图片，对图片内容产生幻觉并据此推理

**典型案例**：
> 任务要求寻找"cheapest blue kayak"，但 DOM 不含颜色信息。Agent 搜索"blue kayak"后仅得到无关商品，陷入持续滚动循环。

> 任务依赖图片中的品牌视觉信息，Agent 盲目猜测品牌为 JBL 并反复搜索，陷入搜索循环。

> Agent 在纯 DOM 模式下无法读取图片内容，对图片产生幻觉（如猜测书的数量、钞票面值），据此做出错误判断。

### 4.2 商品描述不进入 AXTree

95% 的详情页 AXTree 不含商品描述文本。对于需要从描述中提取答案的任务（如"这个商品的材质是什么？"），DOM 模式结构性无法完成。

### 4.3 非视觉脚手架问题（10 例）

#### 4.3.1 动态 UI 后 element_id 失效（下拉/弹窗）

每步刷新 accessibility tree 是正确机制，失败来自两个子类型：

- **子类型 A（模型行为）**：点击下拉后，模型用上一步推断出的旧 element_id 操作，而非读取新 AT 里的真实 ID → 操作无效。
- **子类型 B（AT 表达力）**：下拉展开后 listbox/option 层级复杂，模型无法在新 AT 中识别正确的可点击节点。

*对应修复路径：Phase 3 M1（select fallback）；Phase 1 SoM on 可缓解（坐标交互不依赖 element_id）*

#### 4.3.2 Gallery 网格布局行列不可区分

Gallery 视图（`sShowAs=gallery`）在页面上渲染为多列网格（如 3×N），但 AXTree 将所有 item 序列化为线性列表，不包含行/列/grid 语义。当任务要求"第二行的商品"时，模型无法从 DOM 中区分"第二行"与"第二个 item"。

- task_41：Boats gallery 每行 3 列，模型将第 2 个 item（wellcraft V20，实为第一行第二列）误认为"第二行"，提交错误答案（2500.00 $），score=0。

*SoM/Vision 模式可通过截图感知视觉布局，理论上可避免此类错误。*

#### 4.3.3 长表单编辑时滚动丢失上下文

编辑页（如 item_edit）表单较长，agent 点击某个 textbox 聚焦后，下一步 DOM 视窗因页面滚动而变化，导致 agent 丢失刚才的编辑意图，转而去操作当前视窗中可见的其他字段。

- task_76：任务要求修改 listing 价格为 $85.50。step 3 agent 正确识别到 description 中包含旧价格 "$250"，点击了 description textbox `[2396]` 准备编辑。但 click 只是聚焦，下一步 DOM 视窗滚动到 Price 字段区域，description 不再可见。agent 丢失编辑 description 的上下文，转而点击 Price 字段 `[2400]`，之后 step 5-7 陷入无效 scroll 循环。

*SoM/Vision 模式可通过截图感知页面滚动位置，理论上可缓解上下文丢失问题。*

#### 4.3.4 过滤器 UI 可操作性不足

- 进入过滤器页后无法定位价格输入框
- 只能输入价格下限或上限，无法进行组合搜索
- 过滤条件 UI 在 DOM 中结构混乱，导致操作失败

*与"模型不知道用过滤器"区分：这里是知道要用但做不到*

## 五、模型能力问题（104 例，48.8%）

### 5.1 搜索循环（29 例）

- 反复使用同一关键词搜索（最多 8 次重复同一查询）
- 将任务描述中的位置特征（"第二行的红车"）直接作为搜索词
- 无法组合使用分类下拉框和搜索功能
- 将占位符文本 `exact item name` 字面作为搜索词

**特征**：平均 17.1 步，是步数消耗较高的失败类型。

### 5.2 导航循环（18 例）

- 在详情页和列表页之间反复跳转（click-back 循环）
- 缺乏已访问 item 的记录，重复访问同一商品
- 找到正确目标但未记录，继续无效导航

**特征**：平均 27.9 步（所有类别最高），步数浪费最严重。

### 5.3 事实推理错误（15 例）

模型在数值比较、价格判断等基础推理上频繁出错：
- 将 $1645 判定为在 $1000-$1200 范围内
- 仅设最低价不设最高价，导致过滤结果集不准确
- 误判发布日期，将不满足条件的条目计入
- 将 URL 参数（如 `iPage=2`）误解为页面布局信息（"第二排"）

**特征**：平均 8.0 步即结束，说明模型过早做出错误判断，而非探索不足。

### 5.4 过早结束（12 例）

- 仅点击搜索结果第一个商品即认定任务完成
- 未翻页确认是否有更优结果（如"最便宜"任务仅看了一条）
- 仅凭部分信息就给出答案（如只看到一个价格就回答"price range"）

**特征**：平均仅 2.8 步，步数消耗最少但失败最确定。

### 5.5 目标不可达（模型归因，12 例）

虽然标记为"目标不可达"，但 GLM 归因认为是模型策略不足——理论上 DOM 可完成但模型未采取有效策略：
- 未使用价格过滤器缩小范围
- 搜索策略过于单一，未尝试分类浏览
- 任务意图未提供具体物品名称时，agent 直接搜索占位符文本

**特征**：平均 14.4 步。

### 5.6 答案对齐错误（10 例）

- 错误定位目标元素在页面中的位置（如将 Buick 识别为"第三行第二辆"）
- 凭空捏造不存在的商品 ID 或链接
- 对"最新"/"红色"等属性的事实推理偏差
- 搜索词过于模糊（如 "expensive item"），凭价格高就错误确认

**特征**：平均 6.6 步。

### 5.7 执行停滞（7 例）

- 搜索结果页不展示颜色信息，但 agent 未点进详情页查看
- 未修改排序规则（如改为升序查找最旧 listing）

**特征**：平均 7.7 步。

### 5.8 综合失败（1 例）

- 多种模型能力问题叠加，无法归入单一类别。

## 5A. 高频模型能力缺陷：翻页与排序

> 手动审查发现，以下两类能力缺陷在 classifieds 站点的失败 episode 中**大量反复出现**，是导致搜索循环、导航循环、目标不可达等多类失败的共性上游原因。

### 5A.1 无法翻页（分页控件不可达）

Classifieds 搜索结果通常分多页显示，底部有 `< 1 2 3 4 5 >` 等分页控件。在 AXTree 中这些控件作为 link 元素可见可点击，但模型**从不尝试点击分页**，只会反复 scroll 到页面底部。

**表现模式**：
- Agent 在当前页找不到目标 → scroll down 到底 → 继续 scroll（页面不变）→ 触发 cycle/max_steps 结束
- 多页结果的任务（如"找最便宜的 X"）只看第一页就下结论，或反复搜索不同关键词试图让目标出现在第一页
- 即使 AXTree 中分页链接（`[id] link "2"`, `[id] link "Next"`）清晰可见，模型也不会选择点击

**影响**：所有需要浏览多页结果的任务几乎不可能成功。这涵盖"列出所有满足条件的商品"、"找价格最高/最低的商品"等任务类型，是搜索循环（42 例）和导航循环（30 例）的重要触发因素之一。

### 5A.2 无法使用 Sort By 排序功能

Classifieds 搜索结果页右侧有 Sort By 下拉控件，支持按价格（Price ascending/descending）、日期（Date）等排序。在 AXTree 中该控件以 `combobox` 或 `listbox` 形式出现，理论上可操作。

**表现模式**：
- "找最贵/最便宜的 X" 类任务，agent 从不尝试切换排序方式，而是逐个点击商品手动比较价格
- "找最新的 listing" 类任务，agent 不用日期排序，而是在默认排序结果中猜测哪个最新
- Agent 的 thought 中偶尔提到"应该按价格排序"，但从未执行对应操作

**影响**：不使用排序意味着 agent 必须浏览所有结果才能确定极值（最贵/最便宜/最新），结合不会翻页的问题，实际只能看到第一页的默认排序结果。这导致：
- 过早结束（18 例）：仅凭第一页部分结果就下结论
- 事实推理错误（17 例）：未排序 → 信息不完整 → 错误判断
- 搜索循环：试图用搜索关键词实现排序效果（如搜索 "cheapest chair"）

### 两者叠加效应

翻页 + 排序的双重缺失使 agent 被困在"第一页 × 默认排序"的极小视野内。对于 classifieds 站大量的"找极值商品"类任务，这相当于只看随机选取的一小部分结果就做判断。即使 DOM 信息完整（非视觉类任务），这两个能力缺陷也严重制约了成功率。

### 潜在解法：站点操作先验注入（Avenir-Web EIP）

Avenir-Web (Li et al., 2025, arXiv:2602.02468) 的 **EIP（Experience-Informed Planning）** 机制在任务开始前搜索站点帮助文档，合成 2-4 条导航指令注入 prompt。消融实验显示去掉 EIP 后成功率从 48% 降到 36%（所有模块中降幅最大，-12pp）。

翻页和排序问题的本质不是 UI 不可达（AXTree 中分页链接和 Sort By 控件均可见可操作），而是**模型缺乏站点操作先验**——不知道"搜索结果有多页"、"右侧有排序功能"。这恰好是 EIP 方法的适用场景。

**低成本方案**：为 classifieds 站编写静态操作指南（3-5 条规则），注入 system prompt：
- "搜索结果有多页时，点击底部页码数字或 Next 链接翻页"
- "需要找最贵/最便宜的商品时，先点击右侧 Sort By 按价格排序"
- "需要找最新/最旧的 listing 时，先用 Sort By 按日期排序"

成本为零（静态文本，不增加 API 调用），预期可缓解搜索循环、过早结束、事实推理错误等多类失败。该方案可作为 Phase 3 模块消融的候选实验（M5 站点先验）。

## 七、DOM 模式的结构性上限与启示

> 本节仅基于 DOM baseline 数据推导，不引用其他观测模式实验结果。

### 信息瓶颈

- **99/213（46.5%）** 的失败直接归因于视觉信息不可达——DOM 模式不可逾越的信息鸿沟
- **95% 的详情页 AXTree 不含商品描述**——文本可达信息进一步受限
- 即使模型能力无限，DOM 模式在 Classifieds 站点的理论成功率上限约为 **~55%**

### 效率优化目标

- **搜索循环**（42 例 × 19.3 步）和**导航循环**（30 例 × 28.0 步）合计浪费 ~1,649 步，是 retry/fallback 机制的首要目标
- 脚手架问题平均消耗 16.8 步，模型问题 14.0 步——两者步数消耗接近
- 如果能提前识别视觉类任务并切换观测模式，可避免 99 例 × 16.9 步 ≈ 1,676 步的无效消耗

### 模型能力改善空间

- **事实推理错误**（17 例）和**答案对齐错误**（12 例）属于模型能力上限，路由到更强模型可能改善
- **过早结束**（18 例，平均 2.5 步）可通过验证机制部分缓解

### 站点特殊性

- Classifieds 站点 **74% 的任务涉及视觉属性**（颜色/图片/外观），是三个 VWA 站点中视觉依赖最重的
- 单站 classifieds 的 8.97% 成功率不能代表整体，其他站点（shopping/reddit）视觉依赖更低

## 八、Visual Task 假阳性分析

### 8.1 问题发现

Classifieds 站 234 个任务中，**162 个（69.2%）为视觉任务**——任务 intent 涉及颜色、图片匹配、外观属性等需要视觉信息的内容。DOM 模式下 agent 无法看到截图，但由于 `url_match` 评测类型（到达正确页面即得分），agent 可能通过盲猜导航"碰巧"到达正确页面。

### 8.2 关键数据

| 指标 | 数值 |
|------|------|
| 总 episodes | 234 |
| 视觉任务 | 162（69.2%） |
| 非视觉任务 | 72（30.8%） |
| 原始成功数 | 21（8.97%） |
| **Visual lucky hits** | **19** |
| 真实成功数（非视觉） | 2 |
| **调整后成功率** | **0.85%**（2/234） |
| 非视觉任务成功率 | 2.78%（2/72） |

### 8.3 典型案例

- **task_93 / task_94 / task_98**：任务要求匹配参考图中的视觉属性（颜色、款式），DOM 不含图片语义信息。Agent 在搜索结果中随机点击某个商品，恰好 URL 匹配评测目标，`url_match` 判定通过。这不是 agent 理解了任务，而是盲猜命中。

### 8.4 影响

- DOM 模式 8.97% 的原始成功率中，**90.5%（19/21）是 visual lucky hits**
- 去除假阳性后，DOM 模式的真实成功率仅 **0.85%**，远低于表面数据
- 这进一步印证了 §4.1"视觉信息结构性不可达"的严重性：不仅视觉任务本身无法完成，连看似成功的结果也多为巧合
- SoM 模式无 visual lucky hits（0 个），说明 SoM 模式的成功是基于真实视觉理解

## 十、基础设施噪声分析

> 以下问题在 2026-04-07 的 step 级数据审查中发现，属于实验运行环境引入的系统性噪声，已在下一次重跑前修复。

### 10.1 busy:1 页面加载中间态消耗步数预算

**现象**：VWA 底层 `wait_for_load_state("networkidle", timeout=2000)` 对远程 Classifieds 站点不够长，导致截图/DOM 捕获到半加载页面（AXTree 中 RootWebArea 携带 `busy: 1` 标记）。

**机制**：Runner 在 LLM 调用**之后**才检查 `busy: 1` 并覆盖 action 为 `wait`，导致：
1. LLM 推理已消耗（浪费 tokens + latency）
2. `wait` 仍占用一个 `max_steps` 步数名额

**DOM 条件影响**：

| 指标 | 数值 |
|------|------|
| 受影响 task 数 | 130/234 (55.6%) |
| busy:1 步数占总步数比 | 422/3584 (**11.8%**) |
| 浪费 tokens | 561,278 |
| 浪费延迟 | ~2.9 小时 |
| 到 max_steps 失败且有 busy:1 步的 task | 55 |
| 这些 task 平均浪费步数 | 4.7 步 (15.7% 预算) |

**对分析的影响**：
- **步数消耗**被 busy:1 推高（第六节中的步数含 busy:1 无效步）
- **成功率**可能被压低：55 个到 max_steps 的失败 task 中，部分可能在额外 4.7 步内完成
- **成本/延迟指标**被污染（~12% 的推理成本是 busy:1 浪费的）

**修复**（已合入 runner.py）：将 `busy: 1` 检查提到 LLM 调用之前，命中时跳过推理并执行免费 wait（不消耗 step_idx）。下次重跑将消除此噪声。

### 10.2 type 到 RootWebArea 导致页面全选

**现象**：Agent 错误地将 `type` action 发送到 `RootWebArea`（页面根节点）而非搜索输入框。VWA 的 type 执行流程为：点击元素中心 → `Meta+A` 全选 → Backspace → 输入文本。对 RootWebArea 执行 `Meta+A` 导致页面所有文本被选中（蓝色高亮），后续截图捕获到全选状态。

**DOM 条件影响**：

| 指标 | 数值 |
|------|------|
| 受影响步数 | 24 |
| 受影响 task 数 | 18/234 |
| 重复犯错最多的 task | task_227 (4 次), task_198 (3 次) |

**典型案例**：
- task_0: step_3 将 `type "blue kayak\n"` 发到 `[1200] RootWebArea`，后续步骤截图全部带蓝色全选
- task_227: 4 次将 `type "clock\n"` 发到 RootWebArea，陷入重复循环

**归因**：模型能力问题——4B 模型混淆了搜索输入框和页面根节点的 element_id。所有实例均为搜索重试场景（agent 想重新搜索但选错了元素）。此问题不需要在 runner 层修复，属于 agent 决策质量的自然表现。

### 10.3 JSONL 重启噪声

**现象**：Watchdog 超时重启或 queue 重启导致 JSONL step 文件中出现重复数据（前一次运行的 stale lines + 新运行的 lines），`step_idx` 从 0 重新开始。

**DOM 条件影响**：12 个 task 受影响，共 124 条 stale lines。

**修复**（已合入）：所有 JSONL 读取器（`analysis.py`、`analyze_reason_diagnostics.py`、`digest_enrich.py`、`analyze_confidence_calibration.py`）增加 dedup 逻辑——检测 `step_idx` 重置为 0，仅保留最后一次运行数据。Summary JSON 不受影响（覆盖写入）。

### 10.4 Evaluator 错误

3 个 SoM 条件 episode（task 24, 135, 160）因 OpenAI API key 缺失或 program_html 评测超时导致 `evaluator_error`。DOM 条件未受影响。

**处理**：task 24、135 已通过 `reeval_phase1.py` 离线重评（仍为失败，agent 提交空答案）；task 160 为 program_html 类型，需 live browser 无法离线重评。
