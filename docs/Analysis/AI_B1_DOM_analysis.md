## 三、AXTree 信息可达性分析

基于 `digest_enrich.py` 对 217 条失败 episode 的原始 step 日志和 artifact 进行确定性分析。

### 3.1 商品描述文本不可达

| 指标 | 数值 | 含义 |
|------|------|------|
| 到达过详情页的 episode | 139/217 (64%) | 近 2/3 的失败 episode 至少进入过一次商品详情页 |
| 详情页 AXTree 缺失商品描述 | 132/139 (95%) | **95% 的详情页 AXTree 不含商品描述文本** |
| 详情页 AXTree 平均长度 | 3,374 字符 | 仅含标题/价格/日期/卖家联系方式 |
| 全局 AXTree 平均长度 | 3,167 字符 | 整体信息密度低 |

**关键发现**：Classifieds 站点的商品描述文本（通常包含尺寸、颜色、材质等关键属性）不进入 AXTree。即使 agent 进入了正确的详情页，也无法通过 DOM 读取描述中的答案。

### 3.2 AXTree element_id 引用率

| 指标 | 数值 |
|------|------|
| 平均 element_id 引用率 | 4.8% |

Agent 的 thought 中很少显式引用 element_id，大部分决策基于对 AXTree 文本的语义理解而非精确的元素定位。

### 3.3 视觉关键词回声

| 指标 | 数值 |
|------|------|
| 含视觉关键词的 episode | 162/217 (75%) |
| 其中仅为任务意图回声 | 103/162 (64%) |

在包含视觉关键词（如 red、blue、image）的 thought 中，64% 只是在重复任务描述中的词汇，并未产生新的视觉推理。这表明 DOM 模式下模型对视觉类任务的处理策略是"回声式"的——复述任务要求但无法获取实际视觉信息。

## 四、脚手架 / 表征结构性缺陷（118 例，54.4%）

### 4.1 视觉/图片信息不可达（111 例，占脚手架问题的 94%）

这是 DOM 模式最大的结构性瓶颈。纯 DOM 环境无法获取图片、颜色、视觉属性等信息，导致大量任务在结构上不可完成。

**表现形式**：
- **目标不可达**（58 例）：任务要求匹配视觉属性（颜色、款式、图片内容），DOM 中不含图片语义，agent 无法验证候选商品
- **搜索循环**（16 例）：因无法从视觉确认目标，agent 反复用不同关键词搜索同一目标
- **执行停滞**（16 例）：agent 知道需要视觉确认但无法获取，在页面上反复滚动
- **导航循环**（11 例）：反复进出详情页试图"看到"图片信息，形成 click-back 死循环
- **过早结束**（5 例）：agent 判定视觉信息不可获取，直接放弃任务
- **事实推理错误**（5 例）：无法看到图片，对图片内容产生幻觉并据此推理

**典型案例**：
> 任务要求寻找"cheapest blue kayak"，但 DOM 不含颜色信息。Agent 搜索"blue kayak"后仅得到无关商品，陷入持续滚动循环。

> 任务依赖图片中的品牌视觉信息，Agent 盲目猜测品牌为 JBL 并反复搜索，陷入搜索循环。

> Agent 在纯 DOM 模式下无法读取图片内容，对图片产生幻觉（如猜测书的数量、钞票面值），据此做出错误判断。

### 4.2 商品描述不进入 AXTree

95% 的详情页 AXTree 不含商品描述文本。对于需要从描述中提取答案的任务（如"这个商品的材质是什么？"），DOM 模式结构性无法完成。

### 4.3 筛选器/UI 操作失败（4 例）

- 价格筛选器输入框在 AXTree 中定位困难
- 只能输入单向价格约束，无法完成组合过滤
- 下拉菜单展开后选项在 DOM 中层级复杂，难以操作

### 4.4 其他脚手架问题（3 例）

- 删除操作依赖 JS 确认弹窗，DOM 模式下无法完成

## 五、模型能力问题（99 例，45.6%）

### 5.1 事实推理错误（21 例）

模型在数值比较、价格判断等基础推理上频繁出错：
- 将 $1645 判定为在 $1000-$1200 范围内
- 仅设最低价不设最高价，导致过滤结果集不准确
- 误判发布日期，将不满足条件的条目计入
- 将 URL 参数（如 `iPage=2`）误解为页面布局信息（"第二排"）

**特征**：平均仅 6.8 步即结束，说明模型过早做出错误判断，而非探索不足。

### 5.2 搜索循环（18 例）

- 反复使用同一关键词搜索（最多 8 次重复同一查询）
- 将任务描述中的位置特征（"第二行的红车"）直接作为搜索词
- 无法组合使用分类下拉框和搜索功能
- 将占位符文本 `exact item name` 字面作为搜索词

**特征**：平均 22.3 步，是步数消耗最高的失败类型之一。

### 5.3 导航循环（17 例）

- 在详情页和列表页之间反复跳转（click-back 循环）
- 缺乏已访问 item 的记录，重复访问同一商品
- 找到正确目标但未记录，继续无效导航

**特征**：平均 27.2 步（所有类别最高），步数浪费最严重。

### 5.4 过早结束（13 例）

- 仅点击搜索结果第一个商品即认定任务完成
- 未翻页确认是否有更优结果（如"最便宜"任务仅看了一条）
- 仅凭部分信息就给出答案（如只看到一个价格就回答"price range"）

**特征**：平均仅 4.7 步，步数消耗最少但失败最确定。

### 5.5 目标不可达（模型归因，13 例）

虽然标记为"目标不可达"，但 GLM 归因认为是模型策略不足——理论上 DOM 可完成但模型未采取有效策略：
- 未使用价格过滤器缩小范围
- 搜索策略过于单一，未尝试分类浏览
- 任务意图未提供具体物品名称时，agent 直接搜索占位符文本

### 5.6 答案对齐错误（11 例）

- 错误定位目标元素在页面中的位置（如将 Buick 识别为"第三行第二辆"）
- 凭空捏造不存在的商品 ID 或链接
- 对"最新"/"红色"等属性的事实推理偏差
- 搜索词过于模糊（如 "expensive item"），凭价格高就错误确认

### 5.7 执行停滞（6 例）

- 搜索结果页不展示颜色信息，但 agent 未点进详情页查看
- 未修改排序规则（如改为升序查找最旧 listing）

## 六、步数消耗模式

| 失败类型 | 平均步数 | 特征 |
|----------|----------|------|
| 导航循环 | 27.2 | 步数最高，click-back 死循环 |
| 搜索循环 | 22.3 | 重复搜索是主要浪费源 |
| 目标不可达 | 18.4 | 注定失败但 agent 仍消耗大量步数 |
| 视觉属性 DOM 不可达 | 15.0 | 结构性失败 |
| 答案对齐错误 | 9.3 | 中等消耗 |
| 事实推理错误 | 6.8 | 快速错误决策 |
| 执行停滞 | 6.5 | 早期卡住 |
| 过早结束 | 4.7 | 最少步数，最确定的失败 |

- **高消耗失败**（导航循环 + 搜索循环）：占 28.6% 的失败但消耗最多步数，是效率优化的首要目标
- **快速失败**（过早结束 + 事实推理错误）：步数少但说明模型决策质量差
- **结构性失败**（目标不可达 + 视觉属性不可达）：占 35.9%，agent 平均仍消耗 18 步才停止

## 七、DOM 模式的结构性上限与启示

> 本节仅基于 DOM baseline 数据推导，不引用其他观测模式实验结果。

### 信息瓶颈

- **111/217（51.2%）** 的失败直接归因于视觉信息不可达——DOM 模式不可逾越的信息鸿沟
- **95% 的详情页 AXTree 不含商品描述**——文本可达信息进一步受限
- 即使模型能力无限，DOM 模式在 Classifieds 站点的理论成功率上限约为 **~55%**

### 效率优化目标

- **搜索循环**（34 例 × 22.3 步）和**导航循环**（28 例 × 27.2 步）合计浪费 ~1,520 步，是 retry/fallback 机制的首要目标
- 脚手架问题平均消耗 16.8 步，模型问题 14.7 步——两者步数消耗接近
- 如果能提前识别视觉类任务并切换观测模式，可避免 111 例 × 16.8 步 ≈ 1,865 步的无效消耗

### 模型能力改善空间

- **事实推理错误**（26 例）和**答案对齐错误**（11 例）属于模型能力上限，路由到更强模型可能改善
- **过早结束**（18 例，平均 4.7 步）可通过验证机制部分缓解

### 站点特殊性

- Classifieds 站点 **74% 的任务涉及视觉属性**（颜色/图片/外观），是四个 VWA 站点中视觉依赖最重的
- 单站 classifieds 的 7.3% 成功率不能代表整体，其他站点（wikipedia/shopping）视觉依赖更低

## 八、方法论说明

- **数据来源**：`B1_3mode_classifieds_20260404_141103/phase1_dom_router_0`，234 episodes
- **Digest 文件**：`digest_dom.jsonl`（仅含 DOM 模式，与 SoM/vision 模式物理隔离）
- **归因管线**：
  1. GLM-5.1 batch digest — 对每个失败 episode 的 step 日志 + AXTree 片段进行归因，输出 category / root_cause / is_scaffolding_issue
  2. `digest_enrich.py` 后处理 — 从原始 step 日志和 artifact 提取确定性指标（AXTree 描述可达性、element_id 引用率、视觉关键词回声率等）
- **局限性**：
  - GLM 归因基于 step 日志文本摘要，未直接看到原始截图（DOM 模式无截图依赖，影响有限）
  - task_184、task_187 因 GLM API 错误未自动消化，已通过人工阅读 step 日志补全归因
  - 脚手架 vs 模型的边界在部分 case 中模糊（如"搜索循环"中视觉缺失导致搜索无果，兼具两者特征）
  - 6 个 episode 的 JSONL 行数超过 max_steps=30（因 restart 追加），统计已做 cap 处理

## 九、基础设施噪声分析

> 以下问题在 2026-04-07 的 step 级数据审查中发现，属于实验运行环境引入的系统性噪声，已在下一次重跑前修复。

### 9.1 busy:1 页面加载中间态消耗步数预算

**现象**：VWA 底层 `wait_for_load_state("networkidle", timeout=2000)` 对远程 Classifieds 站点不够长，导致截图/DOM 捕获到半加载页面（AXTree 中 RootWebArea 携带 `busy: 1` 标记）。

**机制**：Runner 在 LLM 调用**之后**才检查 `busy: 1` 并覆盖 action 为 `wait`，导致：
1. LLM 推理已消耗（浪费 tokens + latency）
2. `wait` 仍占用一个 `max_steps` 步数名额

**DOM 条件影响**：

| 指标 | 数值 |
|------|------|
| 受影响 task 数 | 130/234 (55.6%) |
| busy:1 步数占总步数比 | 422/3584 (**11.8%**) |
| 浪费 tokens | 561,278 |
| 浪费延迟 | ~2.9 小时 |
| 到 max_steps 失败且有 busy:1 步的 task | 55 |
| 这些 task 平均浪费步数 | 4.7 步 (15.7% 预算) |

**对分析的影响**：
- **步数消耗**被 busy:1 推高（第六节中的步数含 busy:1 无效步）
- **成功率**可能被压低：55 个到 max_steps 的失败 task 中，部分可能在额外 4.7 步内完成
- **成本/延迟指标**被污染（~12% 的推理成本是 busy:1 浪费的）

**修复**（已合入 runner.py）：将 `busy: 1` 检查提到 LLM 调用之前，命中时跳过推理并执行免费 wait（不消耗 step_idx）。下次重跑将消除此噪声。

### 9.2 type 到 RootWebArea 导致页面全选

**现象**：Agent 错误地将 `type` action 发送到 `RootWebArea`（页面根节点）而非搜索输入框。VWA 的 type 执行流程为：点击元素中心 → `Meta+A` 全选 → Backspace → 输入文本。对 RootWebArea 执行 `Meta+A` 导致页面所有文本被选中（蓝色高亮），后续截图捕获到全选状态。

**DOM 条件影响**：

| 指标 | 数值 |
|------|------|
| 受影响步数 | 24 |
| 受影响 task 数 | 18/234 |
| 重复犯错最多的 task | task_227 (4 次), task_198 (3 次) |

**典型案例**：
- task_0: step_3 将 `type "blue kayak\n"` 发到 `[1200] RootWebArea`，后续步骤截图全部带蓝色全选
- task_227: 4 次将 `type "clock\n"` 发到 RootWebArea，陷入重复循环

**归因**：模型能力问题——4B 模型混淆了搜索输入框和页面根节点的 element_id。所有实例均为搜索重试场景（agent 想重新搜索但选错了元素）。此问题不需要在 runner 层修复，属于 agent 决策质量的自然表现。

### 9.3 JSONL 重启噪声

**现象**：Watchdog 超时重启或 queue 重启导致 JSONL step 文件中出现重复数据（前一次运行的 stale lines + 新运行的 lines），`step_idx` 从 0 重新开始。

**DOM 条件影响**：12 个 task 受影响，共 124 条 stale lines。

**修复**（已合入）：所有 JSONL 读取器（`analysis.py`、`analyze_reason_diagnostics.py`、`digest_enrich.py`、`analyze_confidence_calibration.py`）增加 dedup 逻辑——检测 `step_idx` 重置为 0，仅保留最后一次运行数据。Summary JSON 不受影响（覆盖写入）。

### 9.4 Evaluator 错误

3 个 SoM 条件 episode（task 24, 135, 160）因 OpenAI API key 缺失或 program_html 评测超时导致 `evaluator_error`。DOM 条件未受影响。

**处理**：task 24、135 已通过 `reeval_phase1.py` 离线重评（仍为失败，agent 提交空答案）；task 160 为 program_html 类型，需 live browser 无法离线重评。
