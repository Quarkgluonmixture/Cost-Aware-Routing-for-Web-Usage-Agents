# LLM 与多模态 Web GUI Agent 中面向成本效率的 Routing 全景与输入表示路由缺口

## 核心判断

如果把“routing for cost/efficiency”严格理解为**推理时**为了改善成本–准确率或成本–成功率而做的自适应分配，那么现有工作大体落在三层：其一是**把请求路由给谁**，也就是跨模型池的选择与级联；其二是**让同一模型算多少**，包括早退、层跳过、自推测解码、token/KV 保留预算；其三是**让模型看什么、怎么看**，即提示压缩、历史选择、模态/观察配置、以及输入表示序列化。前两层在 2023–2026 的文献里已经很成熟，而且有明确的理论、benchmark 和系统论文；第三层在 web/GUI agent 中明显更弱，尤其是你关心的“**固定模型下，对同一网页/GUI 状态按任务选择 DOM/HTML/AxTree/screenshot/SoM 等表示**”这一问题，主流工作仍然大多是**固定默认表示 + 消融比较**，而不是训练或部署一个真正的 per-task 表示路由器。citeturn37search0turn38search0turn34search4turn35search0turn41search1turn39search0turn40search0turn40search1turn23search6turn26view0turn22view1

对 web/GUI agent 尤其重要的一点是：现有系统更常做的是**在某一种表示内部做压缩/删减/重构**，比如从完整 accessibility tree 中检索相关行、把线性化 a11y tree 改写成更紧凑的结构化文本、只保留历史截图中的部分 patch，或者改写 HTML/DOM 的文本序列化；相比之下，**在运行时于多种异构表示之间切换**的工作少得多。最接近你所问问题的证据，分别来自 SeeAct 对不同 grounding/观察方式的受控比较、AndroidWorld 与 OSWorld-Human 对 a11y/SoM/截图组合的系统实验、以及 2026 年的 *Read More, Think More* 对 HTML 与 accessibility tree 的重新评估；但这些工作要么不是 web 专属、要么不是 peer-reviewed、要么没有真正做在线 per-task representation routing。citeturn15view3turn26view0turn22view1turn23search6turn12view0turn28view0

## 现有证据能否回答你的问题

就你最精确的问题——**“是否存在 peer-reviewed、systematic characterization，专门研究固定模型下 web agent 的 per-task input-representation routing？”**——我的结论是：**没有发现这样的论文**。最接近的 work 是 *Read More, Think More*，它确实系统比较了 HTML 与 accessibility tree，并明确建议按模型能力和 thinking budget 自适应选择 observation representation，但截至 2026-06 它仍是 arXiv preprint；更早的 peer-reviewed 论文，如 AndroidWorld 和 WebVoyager，要么不是 web 专属、要么并未把问题形式化成 per-task representation router。citeturn23search6turn26view0turn16search9

如果把标准稍微放宽到“peer-reviewed 且带有固定模型、固定任务集下的表示对照”，那么可以列出的只有**局部近邻**，而不是你要的那个问题本身：AndroidWorld 给了 a11y vs SoM 的严格对照，但它是移动 GUI，不是 web；WebVoyager 是多模态 web agent 的代表性系统，但它采用的是固定感知配置，不是对多种网页表示做系统路由；SeeAct 则是最有代表性的异构 grounding mode 比较，但截至我检索到的信息，它仍以 arXiv 预印本形式被广泛引用。citeturn26view0turn16search9turn16search2turn9view5turn15view3

因此，精确的 gap 可以写成下面这段：

**当前缺口不是“没人比较表示”，而是“缺少一个统一、可复现、peer-reviewed 的研究框架，把同一 web 状态的多种序列化模式——如 DOM/HTML、accessibility tree、screenshot、SoM、以及这些表示的压缩或混合版本——置于单一固定 agent/backbone 下，研究何时该看哪一种、何时该混合、以及这种选择能否按任务在线学习”。** 现有工作大多只回答了其中一小块：**哪一种默认表示更好**、**某一种表示该怎么压缩**、或者**某两种表示在某个 benchmark 上谁更占优**；它们很少同时覆盖**任务类型、网站类型、模型能力、思考预算、实时 token 成本与 online success**。citeturn23search6turn15view3turn26view0turn22view1turn29search0turn28view0

## 三句 gap 总结

截至 2026-06，我没有找到**peer-reviewed、systematic、per-task** 地研究“固定 web agent / 固定模型下如何在 DOM/HTML、AxTree、screenshot、SoM 等输入表示之间在线路由”的论文。最接近的证据来自 *Read More, Think More*、AndroidWorld、OSWorld-Human 与 SeeAct，但它们分别受限于**未同行评审、非 web 专属、非在线路由**或**只做模式对照而非学习式 selector**。因此，**“input-representation routing for fixed-model web agents” 仍然是一个清晰、具体、且尚未被系统填平的研究空白**。 citeturn23search6turn26view0turn22view1turn15view3

## 开放问题与局限

这份梳理有两个边界。第一，我把“routing”限定在**推理时的成本–表现分配**，因此没有把纯训练期的 MoE expert routing 作为主轴；第二，2025–2026 有不少最贴近你问题的论文仍是 preprint，包括 *Read More, Think More*、FocusAgent、A11y-Compressor、GUI-KV、GUIPruner、ReVision 等，所以“peer-reviewed 缺口”本身很可能会在未来一到两个会议周期内被填补。citeturn23search6turn12view0turn28view0turn32search0turn30search2turn31search2

如果你要把这个 gap 进一步表述成论文问题，最稳妥的 formulation 不是泛泛地说“representation matters”，而是更细地说：**在固定 backbone、固定 action space、固定 benchmark 评估下，学习一个 per-task / per-step 表示策略 \(\pi_\text{repr}\)，在 HTML、AxTree、SoM、纯截图、以及压缩/混合版本之间分配 token 与视觉预算，并直接优化 success–latency–token cost 三目标。** 现有文献已经分别证明了三件事：表示差异足够大、压缩有收益、环境依赖很强；但把这三件事合成一个统一 router 的论文，我没有看到。citeturn23search6turn22view1turn29search0turn28view0turn11view7
